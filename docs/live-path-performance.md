# 保存履歴を含む監視・送信経路の測定

2026-10-05。[測定スクリプト](../research/benchmark_live_paths.py)で、元の同期・監視・実発注台帳の
登録関係と通常の健全性検査を使う合成環境を測定しました。
[全18試行の生データ](../research/20261005-live-path-benchmark.json)を保存しています。
18試行すべてで計測を完了しました。この件数は、模擬注文の成功件数ではありません。

## 入力と測定区間

通知ジャーナル500・2,500・5,000区間（各1,024記録）と、運用通知1万・5万・10万件を組み合わせ、
時計を固定する方法と実経過時間を反映する方法を各3回測定しました。各試行は別の一時保存物です。
BEGIN・HEARTBEAT/ACK・ENDと送信済み通知を検証してbulk配置し、現在の登録を維持します。
監視の観測処理や同期環境の状態取得を置き換えていません。

監視の時間は`watchdog`の状態観測・保護判定・通知処理を含みます。送信経路の時間は`OrderRuntime`の
生成、確認用contextの取得、確認済みdispatchから模擬receiptの保存、または拒否完了までです。
模擬HTTPの応答と送信後のローカル処理も含み、実通信の時間は含みません。履歴生成・登録・初期同期成功と
初回監視の準備は時間に含めません。

資格情報はメモリ上の合成値、HTTPは`MockTransport`、Windows通知の送信callbackは何もしない処理です。
`socket.socket`と`ctypes.WinDLL`を禁止し、その境界への呼出しがあれば計測失敗にします。
実口座・実キー・実注文・実タスクは使いません。

## 結果

時間は中央値（秒）です。本文量は十進MBで、DB全体の容量とは異なります。

| ジャーナル本文量・運用通知数 | 時計 | 監視 | 送信経路 | 模擬POST・受付 |
| --- | --- | ---: | ---: | --- |
| 102.6MB・10,000件 | 固定 | 0.423 | 2.697 | 各1回・3/3受付 |
| 102.6MB・10,000件 | 実経過 | 0.440 | 3.779 | 各1回・3/3受付 |
| 513.0MB・50,000件 | 固定 | 1.894 | 11.221 | 各1回・3/3受付 |
| 513.0MB・50,000件 | 実経過 | 1.944 | 12.114 | 0回・3/3拒否 |
| 1,025.9MB・100,000件 | 固定 | 3.722 | 21.617 | 各1回・3/3受付 |
| 1,025.9MB・100,000件 | 実経過 | 3.802 | 22.943 | 0回・3/3拒否 |

最大サイズの時計固定の送信経路は21.282〜21.786秒、実経過では22.849〜23.049秒でした。
全試行の監視で条件一覧は空でした。実経過で拒否した6試行は、メモリ資格情報を各1回読み込んだ後、
`dispatch`内で`OrderRuntimeError`を返しました。HTTPへの引渡しは0回です。
生データのこの汎用エラーだけでは、下位の拒否理由を特定できません。

監視では`SegmentedEventJournal.check_history`を1回、`PrivateOperations._verify_archives`を5回呼びました。
送信経路ではそれぞれ10回・20回で、サイズ・時計・受付/拒否にかかわらず同じでした。
これは指定した関数への呼出し回数です。内部の個別SQL読取り回数や解析回数の数値ではありません。

## 時計と期限の扱い

固定時計では待機の指定秒数だけ合成時計を進め、検査中の実経過時間を鮮度・期限へ反映しません。
したがって長い経路を模擬受付できても、実環境で期限内に完了することを示しません。
実経過の方法では壁時計と単調時計に計測中の経過時間を反映し、POST待機も実際に待ちます。
両方法とも準備中は時計を固定し、バックグラウンド同期による鮮度の更新はありません。

合成環境の同期鮮度上限は30秒、監視40秒、口座・気配60秒です。これに加えて現在の送信コードは、
HTTP要求を組み立てた後の`validate_dispatch`を1秒以内に終えることを要求します。
通信のtimeoutは既定5秒、その経過上限は10秒です。これらを測定のために広げていません。
送信経路の総時間と、署名後の1秒判定が測る部分の時間は別です。

約500MB・5万件の実経過条件を[追加で1回測定](../research/20261005-live-path-refusal-check.json)し、
`private_order._reason`の返す固定理由を、返り値を変えずに採取しました。
送信経路12.157秒、HTTP0回で`order_dispatch_deadline_exceeded`を確認しています。
この追加試行は署名後の1秒判定で拒否された証拠です。元の18試行へ理由を遡って付け足してはいません。

## 判断と残件

[保存物単独の測定](retained-history-performance.md)で1GBの全バイト検査が約1秒であっても、
今回の登録済み送信経路では複数回の検査を含み、同じ時間では完了しません。
現在の完全性検査と期限を維持したまま、保存量が送信可否に影響することを確認しました。
検査の削除や鮮度・署名期限の延長へ置き換えません。

Windows 11、Python 3.12.14、SQLite 3.53.1の暖まったローカルI/Oです。全体回帰の終了後に開始しましたが、
測定中には短い証拠採取の開発試験と資料レビューも実行しています。OSキャッシュ破棄・負荷固定・冷えた読取り・
実ディスクの競合条件・スケジューラの独立監視間隔を検証した結果ではありません。
現金・約定・注文の大量履歴、REST/WebSocketの通信、Windows資格情報ストア、実通知の受入も含みません。

全18試行の実装指紋は同じ`d0c8079cb31dc561faa09d860896282aaebc6738ec6d84ac018b70bc5b402af3`でした。
測定スクリプトは`100012b`で保存しています。生データの集約は成功した計測だけを対象とし、
計測失敗があれば別に保持して終了コードを1にします。経路の拒否は計測成功と区別して記録します。

次は実機の保存量・ディスクと同期更新を含む経路を測り、1秒の送信前判定・鮮度・監視間隔に対する
運用量の上限を確認します。改善する場合は同じ保存バイトと状態を検証し続ける設計を先にレビューし、
競合・保存失敗・途中終了時に従来の拒否を維持することを試験します。

再実行には開発依存関係と既存の`tests`補助コードが必要です。新しい出力先を指定してください。

```powershell
$env:OPENBLAS_NUM_THREADS='1'
uv run python research/benchmark_live_paths.py --output research/new-live-path-benchmark.json
```
