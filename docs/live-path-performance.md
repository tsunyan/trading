# 保存履歴を含む監視・送信経路の測定

2026-10-05。[測定スクリプト](../research/benchmark_live_paths.py)で、元の同期・監視・実発注台帳の
登録関係と通常の健全性検査を使う合成環境を測定しました。
[全18試行の生データ](../research/20261005-live-path-benchmark.json)を保存しています。
18試行すべてで計測を完了しました。この件数は、模擬注文の成功件数ではありません。

## 入力と測定区間

通知ジャーナル500・2,500・5,000区間（各1,024記録）と、運用通知1万・5万・10万件を組み合わせ、
時計を固定する方法と実経過時間を反映する方法を各3回測定しました。各試行は別の一時保存物です。
BEGIN・HEARTBEAT/ACK・ENDと送信済み通知を検証してbulk配置し、現在の登録を維持します。
監視の観測処理や同期環境の状態取得を置き換えていません。

監視の時間は`watchdog`の状態観測・保護判定・通知処理を含みます。送信経路の時間は`OrderRuntime`の
生成、確認用contextの取得、確認済みdispatchから模擬receiptの保存、または拒否完了までです。
模擬HTTPの応答と送信後のローカル処理も含み、実通信の時間は含みません。履歴生成・登録・初期同期成功と
初回監視の準備は時間に含めません。

資格情報はメモリ上の合成値、HTTPは`MockTransport`、Windows通知の送信callbackは何もしない処理です。
`socket.socket`と`ctypes.WinDLL`を禁止し、その境界への呼出しがあれば計測失敗にします。
実口座・実キー・実注文・実タスクは使いません。

## 結果

時間は中央値（秒）です。本文量は十進MBで、DB全体の容量とは異なります。

| ジャーナル本文量・運用通知数 | 時計 | 監視 | 送信経路 | 模擬POST・受付 |
| --- | --- | ---: | ---: | --- |
| 102.6MB・10,000件 | 固定 | 0.423 | 2.697 | 各1回・3/3受付 |
| 102.6MB・10,000件 | 実経過 | 0.440 | 3.779 | 各1回・3/3受付 |
| 513.0MB・50,000件 | 固定 | 1.894 | 11.221 | 各1回・3/3受付 |
| 513.0MB・50,000件 | 実経過 | 1.944 | 12.114 | 0回・3/3拒否 |
| 1,025.9MB・100,000件 | 固定 | 3.722 | 21.617 | 各1回・3/3受付 |
| 1,025.9MB・100,000件 | 実経過 | 3.802 | 22.943 | 0回・3/3拒否 |

最大サイズの時計固定の送信経路は21.282〜21.786秒、実経過では22.849〜23.049秒でした。
全試行の監視で条件一覧は空でした。実経過で拒否した6試行は、メモリ資格情報を各1回読み込んだ後、
`dispatch`内で`OrderRuntimeError`を返しました。HTTPへの引渡しは0回です。
生データのこの汎用エラーだけでは、下位の拒否理由を特定できません。

監視では`SegmentedEventJournal.check_history`を1回、`PrivateOperations._verify_archives`を5回呼びました。
送信経路ではそれぞれ10回・20回で、サイズ・時計・受付/拒否にかかわらず同じでした。
これは指定した関数への呼出し回数です。内部の個別SQL読取り回数や解析回数の数値ではありません。

## 時計と期限の扱い

固定時計では待機の指定秒数だけ合成時計を進め、検査中の実経過時間を鮮度・期限へ反映しません。
したがって長い経路を模擬受付できても、実環境で期限内に完了することを示しません。
実経過の方法では壁時計と単調時計に計測中の経過時間を反映し、POST待機も実際に待ちます。
両方法とも準備中は時計を固定し、バックグラウンド同期による鮮度の更新はありません。

合成環境の同期鮮度上限は30秒、監視40秒、口座・気配60秒です。これに加えて現在の送信コードは、
HTTP要求を組み立てた後の`validate_dispatch`を1秒以内に終えることを要求します。
通信のtimeoutは既定5秒、その経過上限は10秒です。これらを測定のために広げていません。
送信経路の総時間と、署名後の1秒判定が測る部分の時間は別です。

約500MB・5万件の実経過条件を[追加で1回測定](../research/20261005-live-path-refusal-check.json)し、
`private_order._reason`の返す固定理由を、返り値を変えずに採取しました。
送信経路12.157秒、HTTP0回で`order_dispatch_deadline_exceeded`を確認しています。
この追加試行は署名後の1秒判定で拒否された証拠です。元の18試行へ理由を遡って付け足してはいません。

## 判断と残件

[保存物単独の測定](retained-history-performance.md)で1GBの全バイト検査が約1秒であっても、
今回の登録済み送信経路では複数回の検査を含み、同じ時間では完了しません。
現在の完全性検査と期限を維持したまま、保存量が送信可否に影響することを確認しました。
検査の削除や鮮度・署名期限の延長へ置き換えません。

## 関数別プロファイル

約102.6MB・5万件の別の合成環境を、[プロファイル用スクリプト](../research/profile_live_paths.py)で
1回調べました。[全関数の呼出し回数と時間](../research/20261005-live-path-profile.json)を保存しています。
これは通知履歴の行読取りを変更する前の`daf0d23`の実装です。
準備・履歴生成・初回監視は含めず、上記と同じ監視区間と送信区間だけで`cProfile`を有効にします。
時計は固定です。解析用の計測負荷が加わるため、実経過条件の期限判定や以前の通常測定と時間を直接比較しません。

| 項目 | 監視 | 送信経路 |
| --- | ---: | ---: |
| プロファイルを含む経過秒 | 2.853 | 13.504 |
| `PrivateOperations._verify_archives`の回数 | 5 | 20 |
| 同関数の累積秒 | 2.499 | 10.544 |
| 同関数だけの秒 | 0.705 | 3.023 |
| `PrivateOperations._verify_delivery`の回数 | 250,000 | 1,000,000 |
| 同関数の累積秒 | 0.656 | 2.741 |
| SQLite `fetchall`の秒（経路全体） | 0.572 | 2.408 |
| SQLite `execute`の秒（経路全体） | 0.226 | 1.676 |
| SHA-256関数の秒（経路全体） | 0.058 | 0.423 |

「累積秒」は呼出し先を含み、「同関数だけ」は含みません。累積時間は重複するので足しません。
SQLiteとSHA-256の行は経路全体の集約で、通知履歴だけの値ではありません。
送信区間では通知履歴検査の累積時間が約78%、その内部の受渡し情報検査が経路全体の約20%でした。
この一例からは、全バイト照合だけを遅延の原因として扱えません。DB読取り・Pythonの行検査・繰返し検査も
改善検討の対象です。測定のために完全性検査や署名期限を変更していません。

監視の条件一覧は空で、送信経路の模擬HTTPは1回で受付されています。時計固定とプロファイル負荷を含む結果であり、
実送信できる保存量の保証ではありません。元の経路と同じ実装指紋で、研究スクリプト2本のSHA-256も記録します。
全関数の呼出し回数・非再帰呼出し回数・自関数時間の合計と、経路側の走査回数を再照合しています。

```powershell
$env:OPENBLAS_NUM_THREADS='1'
uv run python research/profile_live_paths.py --segments 500 --alerts 50000 --output research/new-live-path-profile.json
```

## 行読取りの変更と再測定

通知履歴のSQLは必要な列を順序付きで明示し、そのカーソルだけを位置順のtupleとして取得する形へ変更しました。
他の処理が使う接続の`row_factory`は維持します。保存本文の全バイトSHA-256、descriptor・索引・連鎖・件数、
各行の識別子・本文digest・受渡し情報・日時の検査は削除していません。受渡し情報の検査は、
通常行と保存済み行が同じ関数を使います。走査間のキャッシュは追加していません。

[同じ保存物での比較スクリプト](../research/compare_archive_scans.py)と
[16回の生データ](../research/20261005-archive-scan-comparison.json)を保存しました。
5万件の合成通知のうち49,000件が保存済みのDBを、一つの読取トランザクションで検査します。
旧`daf0d23`の検査関数と変更後の関数を8組、順序を交互にして測定しました。
旧関数は固定されたローカルGit版から取り出し、対象の検査関数以外の依存コードがASTとして一致することを先に検査します。
元DBの前後のSHA-256は一致し、16回すべてで戻り値の最終日時も一致しました。

| 検査関数 | 最小秒 | 中央値秒 | 最大秒 |
| --- | ---: | ---: | ---: |
| 旧版 | 0.269 | 0.290 | 0.315 |
| 変更後 | 0.188 | 0.193 | 0.216 |

この条件では検査関数単独の時間が中央値で約33%短くなりました。暖まった一つの合成DBの比較であり、
送信経路・期限・同期更新・ディスク競合の改善幅を示すものではありません。

続いて、[拒否理由も記録する再測定スクリプト](../research/recheck_live_paths.py)で実経過時計を各3回測りました。
[全9試行の生データ](../research/20261005-live-path-recheck.json)を保存しています。
既存の測定区間・登録・MockTransport・メモリ資格情報・socket/WinDLL禁止を使い、
`private_order._reason`の返り値を変えず、固定理由だけを各測定区間で採取します。
計測の負荷を増やす`cProfile`は使っていません。

| ジャーナル本文量・運用通知数 | 監視中央値秒 | 送信経路中央値秒 | 模擬POST・受付 |
| --- | ---: | ---: | --- |
| 102.6MB・10,000件 | 0.525 | 3.965 | 各1回・3/3受付 |
| 513.0MB・50,000件 | 1.863 | 14.314 | 0回・3/3拒否 |
| 1,025.9MB・100,000件 | 3.413 | 22.957 | 0回・3/3拒否 |

全9試行で計測を完了し、監視条件は空でした。拒否した6試行すべてに
`order_dispatch_deadline_exceeded`を記録しました。送信経路の実測値は前回を一律に下回っておらず、
経路全体の高速化や1秒の署名期限の解消を確認した結果ではありません。前回とOS負荷を固定した比較でもありません。
検査関数単独の比較と、登録済み経路の時間は別に扱います。署名期限や鮮度の上限を広げていません。

各試行の監視の走査回数はjournal 1回・monitor 5回、送信経路は10回・20回で、前回と同じでした。
実装指紋は全9試行で`c635050334fa680666c538215dd9c7dd691b7404db308943b67096421e2e8b1a`でした。
実装指紋が変わるため、既存の実環境へ適用する場合には通常の再承認が必要です。
実口座・実タスクに適用する工程は行っていません。

```powershell
$env:OPENBLAS_NUM_THREADS='1'
uv run python research/compare_archive_scans.py --output research/new-archive-scan-comparison.json
uv run python research/recheck_live_paths.py --segments 500 2500 5000 --alerts 10000 50000 100000 --clock-mode elapsed --samples 3 --output research/new-live-path-recheck.json
```

## 測定の限界と次の検証

Windows 11、Python 3.12.14、SQLite 3.53.1の暖まったローカルI/Oです。全体回帰の終了後に開始しましたが、
測定中には短い証拠採取の開発試験と資料レビューも実行しています。OSキャッシュ破棄・負荷固定・冷えた読取り・
実ディスクの競合条件・スケジューラの独立監視間隔を検証した結果ではありません。
現金・約定・注文の大量履歴、REST/WebSocketの通信、Windows資格情報ストア、実通知の受入も含みません。

全18試行の実装指紋は同じ`d0c8079cb31dc561faa09d860896282aaebc6738ec6d84ac018b70bc5b402af3`でした。
測定スクリプトは`100012b`で保存しています。生データの集約は成功した計測だけを対象とし、
計測失敗があれば別に保持して終了コードを1にします。経路の拒否は計測成功と区別して記録します。

次は実機の保存量・ディスクと同期更新を含む経路を測り、1秒の送信前判定・鮮度・監視間隔に対する
運用量の上限を確認します。改善する場合は同じ保存バイトと状態を検証し続ける設計を先にレビューし、
競合・保存失敗・途中終了時に従来の拒否を維持することを試験します。

再実行には開発依存関係と既存の`tests`補助コードが必要です。新しい出力先を指定してください。

```powershell
$env:OPENBLAS_NUM_THREADS='1'
uv run python research/benchmark_live_paths.py --output research/new-live-path-benchmark.json
```
