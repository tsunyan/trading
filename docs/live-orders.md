# 実口座専用の注文台帳と送信API

2026-10-03。単一USD/JPYの通常新規注文と建玉IDを指定した決済を、専用台帳・有効化・
注文直前リスク検査・[永続POST制御](post-control.md)・[受付記録](order-receipts.md)に接続しました。
検証は合成HTTPと一時的な専用台帳で行っています。GMO口座は未準備で、実口座の有効化や送信は行っていません。

## 保存先と有効化

`LiveOrderJournal`は新しいディレクトリに`live-orders.sqlite`を作ります。
modeは`live-execution-v1`、初期状態はDISABLEDです。オフラインの`OrderJournal`や
paper DBを読み替えたり、modeを書き換えて昇格させたりしません。
既存GET制御に紐付いたPOST制御を指定し、一つのPOST制御に一つだけ永久登録します。
別保存先による停止迂回、登録表や台帳の欠落・破損、口座リスク設定の書換えを拒否します。
同じ所有権はキーやプロセスをまたいで使いますが、別PC・別制御・業者画面の操作は制御できません。

`activate`には次を明示的に渡します。

| 入力 | 内容 |
| --- | --- |
| LiveApproval | 口座ID、設定・実装のSHA-256、受入時刻、失効時刻、5種類の証拠参照 |
| 証拠参照 | 本人性、業者ルール、読取受入、開始口座、履歴についての参照名と資料のSHA-256 |
| confirmations | live-orders、account-identity、broker-rules、read-acceptance、complete-account、external-writers-pausedの全項目 |
| expected_revision | 保存済みの有効化状態のrevision |

証拠参照と確認項目は運用者が受入済みと申告した情報です。プログラムがその資料の内容や業者口座本人性を
自動認証したことにはなりません。有効期間は最大7日、未受入・失効・停止では送信できません。
実装の識別子は署名・リスク・claim・受付・GET/POST制御など12モジュールの内容と、
Python・httpx・Pydanticのバージョンを含みます。実装や設定が変わると旧許可をそのまま使えません。
コード更新後も、保存済み設定・紐付け・チェックサムが正しければ台帳を開けます。
状態確認、受付記録の保存、結果不明の記録、GET証拠による照合、明示停止を続けられます。
`snapshot()`の`implementation_matches`と`live_enabled`は更新後にfalseとなり、
新規送信の準備・claim・送信直前の検査で旧コードの許可を拒否します。
実装識別子を取得できない場合も状態確認と停止を可能にし、送信と再承認を拒否します。

明示停止のない台帳の再承認時は`activation_context()`で現在コードに対応する設定・実装SHA-256とrevisionを取得し、
それらを含む新しい`LiveApproval`と全確認項目で`activate()`を呼びます。
この取得だけでは台帳を書き換えず、承認成功時だけ保存識別子と許可を同時更新します。
以前の設定・実装SHA-256は有効化履歴に残します。口座・制御の永久紐付けと注文履歴は維持します。
未確定注文が残る場合は先に照合を終える必要があり、明示停止やリスク停止を再承認で解除できません。
明示停止後は[専用の再開手続き](order-restart.md)を使い、完全な注文・口座照合と停止原因の確認、
現在コードでの新しい許可を要求します。損失による新規停止は保持します。
チェックサムは署名や、悪意あるSQL編集・バックアップ巻戻しへの防御ではありません。

## 口座証拠とリスク

この台帳でも[口座ゲート](account-guard.md)を必須にします。初期は建玉なし・固定の開始現金、
途中の入出金なしという既存ゲートの条件です。新しい完全な正規化`AccountSnapshot`と気配を
信頼する供給側から受け取り、口座ID・現金・建玉・有効注文・評価・余力を照合してから発注できます。
現在の`AccountReadReport`は本人性・同一時点・履歴完全性が未証明です。その診断結果を
`complete=true`へ自動変換する経路は追加していません。

残高・気配の鮮度、市場状態、スプレッド、注文額、総建玉額、レバレッジ、維持率、余力、
未約定注文数、損失額、ドローダウン、決済建玉・残量・既存拘束を検査します。
損失による新規停止は再起動後も保持し、他の検査に通る建玉指定決済だけを許可します。
口座不整合・明示停止は新規も決済も止めます。

## 送信の順序

`PrivateOrderClient`は明示した`SecretStr`のキーと専用台帳を受け取り、`submit(client_id, quote=...)`で送信します。
資格情報の自動読込、任意URL・任意本文の送信、CLIからの発注はありません。
実口座への実行には運用者による受入と有効化を別途必要とします。

1. 保存した意図・有効化・実装・設定を確認する。
2. 共通POST制御のOS所有権と要求SHA-256を保存し、1.1秒待つ。
3. 待機後の時刻でリスクを再検査し、有効化の確認とSUBMITTINGへのclaimを同じDB transactionでcommitする。
4. 正確な本文bytesを署名し、停止・所有者・claim・設定・実装を送信直前に再確認する。
5. 固定したGMOホストへ1回だけPOSTし、応答を厳密に解析する。
6. 生の受付本文を保存せず、受付の識別子・状態・時刻・SHA-256をcommitする。
7. 保存後にPOST枠を正常完了する。注文はGET照合までRECONCILINGに保持する。

他のプロセスやスレッドがこのPOST所有権を持つ間、通常の台帳変更は拒否します。
同じlimiterオブジェクトを別スレッドへ渡しても、送信所有者を代用できません。明示停止は処理中でも保存できます。
保存したclaimは時間経過で解除しません。注文状態だけがPREPAREDへ書き戻されても、
履歴のSUBMITTINGを検査して再送を拒否します。準備した本文・口座証拠と履歴の一致も確認します。

ローカルで送信前に確定した通常のリスク拒否は、注文をPREPAREDに残してPOST枠だけ正常完了します。
claim後の通信・時刻・応答・保存・後片付けの不明では、再試行せず台帳とPOST制御を停止します。
受付後に保存が中断した場合もSUBMITTINGが残り、送られなかったと推測しません。
TLS検証は有効、環境のproxy/cert上書き・redirect・HTTP transportの再試行は無効です。
通信は各phaseのtimeoutと応答全体の経過時間を検査し、本文は最大64,000 bytesです。
認証ヘッダーとcookieを後片付けし、業者・httpxのエラー本文を表示・保存しません。
クライアントの終了処理失敗はPOST制御に`order_cleanup_failed`として記録し、手動停止と区別します。
先に保存した結果不明・明示停止・時計異常の理由とclaimを保持し、受付済み記録を取り消しません。
キーを破棄してクライアントを閉じ、新しい送信やトークン限定の停止解除を拒否します。
低レベルtransportの注入は信頼するテスト用の差替えで、sandbox境界ではありません。

## 残る接続と受入

ライブラリの送信経路まで実装しましたが、実用化完了ではありません。
資格情報ストア・読取ランタイム・完全な口座証拠供給側・既知注文カタログ・独立監視との実運用接続、
非終端の結果不明・ID不明の復旧、戦略の昇格と発注との接続を進める必要があります。
[通常注文の取消HTTP](live-cancel.md)を追加しました。有効な許可と新しいGET証拠を確認し、
単一親注文IDの取消を一度だけ送ります。受付保存後も取消待ちと予約を保持し、部分約定・
履歴不完全を自動的に確定しません。中断した取消も同じGET調査CLIで照合できます。
停止を保持した対象限定の取消許可も保存できます。期限切れ・コード更新後の残注文を指定して
許可しますが、通常の発注許可、POST停止、未解決claimは解除しません。
[結果不明注文のGET照合CLI](order-recovery.md)は業者の注文IDを明示して使用できます。
POST停止中も元のGET制御で調査し、照合証拠を保存します。claim・停止・履歴不完全の判定を維持し、
未受付の推測や発注再開は行いません。
[終端結果のclaim解消](order-resolution.md)は完全な終端証拠・全口座照合と明示確認を要求します。
claimの解消後もPOSTと実口座台帳を停止し、旧クライアントを使用できない世代に進めます。
専用台帳の`begin_cancel`は所有中のPOST取消枠を必須にします。
停止後の`private_order_restart`は証拠と新しい確認を要求し、未解決claimや損失停止を解除しません。
業者側との原子的なsnapshot、検査後の外部操作との競合、別PCでの操作は証明していません。
口座準備後の読取・Windows資格情報ストア・小額発注・業者履歴との会計一致を確認する工程が残っています。

## 検証

```powershell
uv run pytest tests/test_private_order.py tests/test_order_receipts.py tests/test_order_journal.py tests/test_account_guard.py tests/test_post_control.py -q
```

固定ホスト・本文署名・両claim、3種類の受付、新規停止後の成行/指値決済、
待機中の口座・気配期限切れ、許可・設定・コード・保存物の不一致、HTTP/応答/後片付けの障害を合成検証しました。
実プロセスは注文claim後、HTTP応答後の保存前、受付commit後、POST完了commit前で終了させ、
一度だけの模擬HTTPと未完了記録の保持を確認しました。実口座への注文結果の証拠ではありません。
トークン限定の復旧後も、実口座台帳の紐付け・注文状態・許可期限・明示停止が変わらないことを確認しました。
コード更新後の読取り・照合・明示再承認、未確定注文と消費済み送信の再使用拒否、
HTTP後にコードが変わっても受付が保存されること、最終送信検査時の変更でHTTPが送られないことを検証しました。
