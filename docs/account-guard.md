# 口座照合・注文直前リスクゲート（オフライン）

2026-09-29。実送信・APIキー読込は引き続きありません。
既存のペーパー観測の設定・固定コア・DB・スケジュールは変更しません。

## できること

- 注文台帳の約定履歴から残高・建玉・平均取得価格・実現損益を再計算する。
- 口座識別、残高、建玉のID・方向・数量・平均価格、未約定注文と残数量を照合する。
- 売買気配で評価した資産と口座評価額を照合する。不完全な口座取得、
  外部注文・外部建玉、説明不能な残高差異を検出したら永続停止する。
- 注文処理中、気配・口座の古い／未来の時刻、口座より新しい注文証拠、
  過去の口座スナップショットの再取得は、その更新だけを拒否する。
  直前の照合証拠は保持し、注文状態・約定変更による無効化とclaim時の鮮度検査は継続する。
  注文照合の完了と新しい口座・気配の取得後に再試行できる。
- 注文のclaim直前に、気配・口座状態の鮮度、市場状態、スプレッド、注文額、総建玉額、
  レバレッジ、維持率、余力、未約定注文数、損失額、最大ドローダウンを検査する。
- 口座スナップショットがまだ新しくても、注文状態や約定が変わったら照合結果を無効にする。
- 新規・未約定注文の証拠金と費用を保守的に予約計算する。価格保護の境界で新規約定した場合の
  即時評価損（買値とBid、売値とAskの差）も資産から差し引いて検査する。
  未約定の決済を、すでに建玉が減ったものと扱わない。
  買いと売りも相殺せず、総額でリスクを数える。
- 決済対象の建玉ID・方向・残量・既存決済注文への予約数量をチェックする。
- リスク判断と送信準備状態への更新を、同じSQLiteの排他トランザクションで確定する。

## 二種類の停止

| 状態 | 新規注文 | 確認済み建玉の決済 | 注文照合・取消 |
| --- | --- | --- | --- |
| 損失額／DD上限による新規停止 | 不可 | 建玉・数量・鮮度等の検査に通れば可 | 可 |
| 口座の不整合等による全体停止 | 不可 | 不可 | 可（取消は従来どおり確認済み注文のみ） |

停止状態・口座評価額の最高値はDBに残り、再起動や値戻りで解除されません。解除コマンドはありません。
緊急時に取引所側で建玉を管理する手順は、実口座への接続前に別途必要です。
単なる注文額超過や一時的な気配の期限切れは、そのclaimを拒否しPREPAREDのまま記録します。
取消が明示的に拒否された場合はWORKING／PARTIALに戻り、取消を再試行できます。
取消受付だけでは完了と扱わず、通信結果が不明な場合も新規注文を解放しません。
終了済み注文の同一内容を再取得しただけでは、保存済みの証拠や口座照合を無効化しません。
未発注の想定費用だけで損失上限を超える場合も拒否しますが、未発生の損失による永続停止にはしません。

## デモ

```powershell
uv run python -m trading.execution_lab guard-demo --directory runs/account-guard-demo
uv run python -m trading.execution_lab status --directory runs/account-guard-demo
```

未使用のディレクトリを指定してください。既存台帳は上書きしません。
デモは「初期口座照合 → 模擬新規約定 → 値下がり・新規停止 → 再起動 → 追加買い拒否 →
建玉指定の決済 → 残高照合」を実行し、`report.json` と `order-lab.sqlite` を保存します。
すべて合成値です。デモの100円の損失上限や4%の証拠金率等はテスト値で、実運用の推奨値や業者条件ではありません。

Pythonからは `OrderJournal.create(..., account_policy=AccountPolicy(...))` で
ガード付きの新規台帳を作成します。完全な正規化スナップショットを `update_account` に渡し、
`begin_submission(..., quote=..., now=...)` で再度鮮度とリスクを検査します。
ガード付き台帳はポリシーや照合結果を省略してclaimできません。

前段階の `demo` とポリシーなしの `OrderJournal.create` は、注文ライフサイクル単体用の
旧オフライン台帳として残しています。こちらには口座ゲートがなく、`account_guard` はnullです。
どちらも実送信はできず、旧台帳を実口座台帳に転用・自動昇格する機能もありません。

## 対象と限界

- USD/JPY・初期建玉なし・固定初期残高・途中の入出金なしの模擬口座に限定。
  既存建玉の引継ぎ、入出金、残高調整を無断で吸収・再基準化しません。
- AccountSnapshot等は内部の正規化契約であり、GMO APIのJSONをそのまま解釈するパーサーではありません。
  手数料は「正の支払額」、決済損益と決済スワップは符号付きとして計算します。
  生APIの符号・通貨単位・丸め・口座IDの扱いを確認し、変換する工程が残っています。
- 未決済スワップ額は正規化口座値を使います。スワップカレンダーによる独立再計算は未実装です。
  建玉がないのに未決済スワップが残る入力は拒否します。
- 約定の照合が先、口座の照合が後です。同一時刻の約定は約定ID順で再計算します。
  実APIでこの順序が成立するかは未確認で、実接続前に順序と訂正処理を検証します。
- 完全性フラグは呼出側の責任です。ページング、取得間の約定、反映遅延への対応を自動化した
  実APIコレクターはまだありません。単一口座の一貫したスナップショットを保証できなければ停止します。
- 金額・価格の許容差、証拠金率、費用バッファ等は明示設定です。取引所条件の自動取得・固定・検証は未実装です。
  ブローカーの余力と、保守的な計算上の余力の小さい方を使います。
- 損失額は固定初期残高からの累計損失です。「日次損失」ではなく、日付でリセットしません。
  DDは観測済み評価額の最高値基準であり、観測間の最大損失を保証しません。
- 現在の台帳は未解決注文を同時に1件までに制限します。口座ゲート側の予約額計算を用意していますが、
  複数注文の並列執行はまだ有効にしていません。
- 価格保護、スプレッド、市場状態などで決済も拒否され得ます。自動的な無制限成行への切替はありません。
- claim後、実送信までに価格や口座が変わる問題は未解決です。将来の送信アダプターで
  有効期限、実行直前検査、外部操作との競合、通信断時の照合を追加する必要があります。

次の接続段階は、実送信より先に「読み取り専用の口座取得・正規化・完全性確認」を実装することです。
口座開設後には実データによる照合が必要で、今回のテスト合格は実運用の承認ではありません。
