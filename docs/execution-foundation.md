# 実取引に向けたオフライン注文処理基盤

作成: 2026-09-29。収益性の承認・実運用への昇格ではありません。

## 今回できたこと

GMOコインの外国為替FXを想定し、口座・APIキーなしで注文処理を検証できます。
**実注文を送信するHTTPクライアント、認証情報の自動読込、live発注モードは実装していません。**
2026-09-30に別モジュールとして[GET専用HTTPクライアント](private-read.md)を追加しました。
明示認証情報による読み取り用で、この注文基盤とは接続していません。
APIキーを環境変数に入れても実注文は送られません。既存のペーパー観測・自動実行にも接続していません。

| 部分 | 対応内容 |
| --- | --- |
| 注文生成 | USD/JPY、通常注文のみ。新規／建玉IDを指定した決済、成行／指値 |
| 注文検査 | 正の整数数量、指定された最小・最大数量・刻み、価格刻み、参照元本上限 |
| 価格保護 | 成行BUYにupperBound、SELLにlowerBoundを必須化。無制限の成行は生成しない |
| 署名 | GMO仕様のHMAC-SHA256。POST本文の正確なバイト列を署名。GETのqueryは署名に含めない |
| 取消・照会 | 親注文IDを指定するcancelOrders、orderIdを指定するorders／executionsの要求生成 |
| 台帳 | 注文意図、状態、約定証拠、イベントを専用SQLiteに保存 |
| 発注受付 | POST用の厳密な解析と永続保存。受付だけで約定・失効・完全性を確定しない |
| 重複防止 | 一度claimした注文意図は再送不可。同じ顧客IDの内容変更を拒否。未解決注文は同時に1件まで |
| 照合 | 顧客ID・注文ID・親ID・銘柄・方向・新規／決済・数量・価格保護・約定IDの整合性を検査 |
| 障害 | 応答消失、再起動、部分約定、取消と約定の競合、失効、古い証拠、矛盾した証拠をテスト |
| 停止 | 不整合で永続停止。停止後も照合・確認済み注文の取消は可能。自動再開機能なし |

実装は `src/trading/broker_contracts.py`、`order_journal.py`、`execution_lab.py`。
2026-10-03に[注文POSTの受付記録](order-receipts.md)を追加しました。後のGET照合では、
保存した受付の親注文ID・注文ID・終端状態のヒントとの一致も検査します。
外部サービスから取得した実際の注文応答ではなく、公式のフィールド定義に合わせた合成応答で検証しています。

## デモ

リポジトリで、未使用の出力先を指定します。既存ディレクトリは上書きしません。

```powershell
uv run python -m trading.execution_lab demo --directory runs/execution-lab-demo
uv run python -m trading.execution_lab status --directory runs/execution-lab-demo
```

デモの流れ:

1. 1,000通貨の新規注文意図を記録してclaimする（ネットワーク送信なし）。
2. 応答消失を模擬し、DBを開き直す。再送が拒否されることを確認する。
3. 照合で500通貨の部分約定が判明する。
4. 取消要求の受付を模擬する。まだ取消済みとは扱わない。
5. 取消と競合して残り500通貨も約定した証拠を入力し、全量約定と判定する。
6. 建玉IDを指定した1,000通貨の決済注文と、その約定を模擬する。

`order-lab.sqlite` と `report.json` を保存します。reportの `live_enabled` はfalse、
`synthetic_only` はtrueです。デモの価格・手数料・損益は合成値で、投資結果や収益予測ではありません。
デモの数量上限等もテスト用の仮値です。現在の業者ルールや実口座の許容リスクを示しません。

## 状態と安全側の判断

通常は PREPARED → SUBMITTING → WORKING/PARTIAL → FILLED/CANCELED/EXPIRED。
応答が途切れた場合はUNKNOWN、証拠が不十分ならRECONCILINGに留めます。
取消受付後はCANCEL_PENDINGで、最終状態を注文情報と約定情報で照合するまで追加注文を止めます。

- SUBMITTINGへの遷移は、要求を呼出側へ返す**前**にcommitします。送信直前に停止した場合も、
  送信されていないと推測して再送しません。安全のため手動調査が必要になる場合があります。
- clientOrderIdが同じなら業者が重複を必ず排除する、という仮定はしていません。
  ここで保証するのはこの台帳内の一度だけのclaimで、ネットワーク全体のexactly-onceではありません。
- 注文一覧に見つからないこと、空応答、HTTPエラー、APIの非ゼロstatusを
  「不成立が確定した」と解釈しません。拒否理由の分類は未実装で、調査・照合側へ倒します。
- executions_completeは既定false。現在はデモ・テストの呼出側だけが、完全な合成証拠だと指定します。
  **実際の収集処理で無条件にtrueを設定してはいけません。** APIのページング、反映遅延、
  取得間の約定などを考慮した完全性の確認は今後の実装です。
- EXECUTEDでも数量が足りなければRECONCILING。約定IDの重複は一度だけ計上し、内容の変更を拒否します。
- 完了後に新しい約定が現れるなど矛盾した証拠が来たら、最後の整合した状態を残して停止します。
- 監査イベントに署名ヘッダー・キー・生のエラーメッセージを保存しません。
  署名関数の返却ヘッダーは秘密情報です。reprでは隠しますが、直接表示・保存してはいけません。
- 注文意図・価格保護のチェックは、実口座の総建玉・維持率・損失額のリスク制御の代わりにはなりません。
  特にSELLのlowerBoundは価格下限であり、約定元本の上限を保証しません。

## 実口座へ接続する前の残り

2026-09-29追記: [口座照合・注文直前リスクゲート](account-guard.md)を、正規化した模擬口座向けに追加しました。
以下の3・4・6は、内部ロジックの一部が実装済みです。生APIの取得・正規化と実口座検証は引き続き未実施です。

1. 利用業者・口座を確定し、現行の商品ルール、API権限、利用条件を再確認する。
2. キーの安全な保管、固定ホスト・TLS・時刻同期・レート制限・timeout・ログの秘匿化を備えた
   private通信アダプターを追加する。通信失敗時の注文POST自動再試行は禁止する。
3. 最初は読み取りだけで、口座ID・残高・建玉・有効注文・約定履歴を取得する。
   ページング・反映遅延・外部操作を含めた完全な照合を実装する。
   応答消失でorderIdが不明な場合の検索経路と、検索できない場合の手動復旧も必要。
4. 鮮度を検証した気配と口座状態で、注文数・未約定を含む資金予約・総建玉額・損失・
   維持率・レバレッジを検査する。決済では建玉の存在・方向・残量・既存決済注文との競合も検査する。
5. 戦略の判断IDと注文意図を安定して結び、再起動時の全口座照合、監視、停止・復旧手順を整える。
6. 実口座専用の台帳・口座識別・実行コード固定・明示的な有効化と注文直前ゲートを設ける。
   今回の合成台帳やペーパーDBを実口座台帳へ転用しない。
7. 戦略の採算検証と、ユーザーによる資金・損失上限・実注文開始の承認を別に得る。

したがって「口座とキーだけ用意すれば直ちに実運用できる」状態ではありません。
口座がなくても検証できる土台を先行させたもので、実接続・実約定・実残高の検証は未実施です。

## 仕様の根拠

2026-09-29に [GMOコイン外国為替FX公式APIドキュメント](https://api.coin.z.com/fxdocs/) の
認証例、新規注文、決済注文、注文の複数キャンセル、注文情報取得、約定情報取得を確認しました。
暗号資産用APIとは異なり、FXの取消要求は `/v1/cancelOrders` で親注文IDを使用します。
APIの変更に備え、実接続時には再確認が必要です。
