# USD/JPYを実践で使うための実装計画

開始日: 2026-10-03

目的は単一銘柄USD/JPYについて、定期観測から実口座の状態照合、明示的な発注、障害時の停止と
復旧までを実用可能にすることです。日本株と複数銘柄は後回しにします。
口座は未準備のため、実口座受入はコードと合成通信の検証を終えた後に実施します。
通知先はWindowsデスクトップです。キーをチャットに記載する運用にはしません。

実装を追加するたびに既存の凍結口座の条件を確認します。口座の再作成・履歴の補正・
研究上のcandidateから発注許可への自動変換を前提にしません。
現金会計・注文照合の未確認条件は発注前に明示し、確認できない場合は停止します。
この計画の工程が残っている間、FX実用化の目標を達成済みとは扱いません。

  拘束のGET接続14件・停止理由競合の追加1件・永続POST制御33件・注文受付89件・実口座送信57件・
  トークン限定復旧29件・タスク定義の文字コード4件・正常終了の追加3件・通知反映遅延12件を含む
  全1767テストが合格しました。

- 実プロセスの途中終了、OSロック解放、実体Pythonの時間切れ終了、約定commit後の再試行で
  二重約定が起きないこと、通知の再試行、既存約定の非再通知を確認しました。
- Windowsがテストtoastを受け付けることを確認しました。通知の見え方・既読までは証明しません。
- 実際のGMO公開APIによる1周期の実行は`market_closed`で正常終了し、開始・終了・所要時間を保存しました。
- 13:25〜13:27 JSTにWindowsの観測・監視タスクを登録して実行し、両タスクの終了コード0と

- 既存観測のmanifest、設定、売買コア、paper口座を継続しています。
- 13:50 JSTの観測は`market_closed`で正常終了し、遅延・継続中の障害条件・未送信通知はありませんでした。
- 明示した現金台帳の証拠と一致し、完全約定した注文は後続REST再取得から外します。
  部分約定と新しい通知は再取得し、過去の計上証拠を現在の口座証明へ変換しません。
- 同一接続で40注文を順に計上する合成試験では、毎回新しい1注文だけを取得しました。
  内容矛盾の永続停止、再起動時の重複防止、取得中の通知・台帳変更・破損の拒否も確認しました。
- `SegmentedEventJournal`、`end_for_rollover`、`close_for_rollover`を追加しました。
  同じDB内で30区間の記録を保存し、旧書込み・ACK不明・未計上約定・破損を拒否しました。
  切替commit前後のプロセス終了、3接続の購読・トークン削除・新しいREST観測も合成検証しました。
- [StreamControl](stream-control.md)を追加しました。安定したOSロックを保持し、ネットワーク操作前に
  RUNNINGを保存します。停止・途中終了は自動解除せず、所有者不在・末尾・ACK・計上証拠の確認付きで復旧します。
- [PrivateStreamSupervisor](private-supervisor.md)を追加しました。受信中の定期REST取得、正常な通知競合の
  上限付き再試行、容量・時間・イベント数による予定切替を行います。古い結果は新接続に持ち越しません。
- 容量8・9記録で20約定を複数接続にまたがって一度ずつ計上し、各注文の取得も1回になることを確認しました。
  REST期限超過・残高不一致・後片付け不明・OSスレッド起動失敗を永続停止し、停止中の自動再接続を拒否しました。

- [実口座読取CLI](private-sync.md)を追加しました。明示した資格情報参照・GET制御・現金台帳・既知注文を
  保存した設定に紐付け、起動時の設定ハッシュ・revision・末尾を検査します。
  実際のGETクライアント・Reader・TokenClient・Supervisorを通して、通知約定を一度だけ計上しました。
  認証失敗時の両制御の停止、応答しないRESTの所有権保持、口座＋注文の共有取得予算、ローカル復旧も確認しました。
- 同じGET制御には同期環境を一つだけ登録し、別ディレクトリによる停止迂回と同時登録の競合を拒否します。

- 既知注文の追記専用カタログと`register-order`を追加しました。固定設定を変更せず、稼働中の
  次回取得でも新しい対応を参照できます。競合登録、保存commit前後の実プロセス終了、欠落・破損の
  拒否、旧環境の明示移行とmanifest保存中断を合成検証しました。登録で停止は解除しません。

- `reconcile-stopped`を追加しました。旧所有者がいない停止状態で保存済み約定の新しいGET証拠を
  取得し、一致分を計上します。停止解除・再接続は別の明示復旧です。23件の試験で内容矛盾・
  ACK不明・末尾競合・応答しないGETを拒否し、計上commit前後の実プロセス終了後も一度だけ計上しました。

- [Private同期の独立監視とWindows通知](private-operations.md)を追加しました。永続停止・実OS所有者不在・
  照合成功の停滞・GET停止・現金台帳停止・保存状態の確認不能を記録します。同じ障害を重複通知せず、
  失敗した送信を同じtoast IDで再試行します。既読操作は停止を解除しません。
  22件の試験で実プロセス終了、保存状態の欠落・破損、通知失敗・送信後の中断を確認しました。
  一時的な合成環境のPrivateテストtoastを実Windowsへ送り、受け付け1件・失敗0件を確認しました。
  実口座の障害や人による既読の証拠ではありません。

- Private監視タスクの定義と登録スクリプトを追加しました。資格情報を含まない独立監視を
  ログイン時・60秒周期で実行します。9件の試験でパスの受渡し・実体Python・PlanOnlyを確認しました。
  一時的な合成環境ではWindowsへの登録・更新・実行が成功し、16:38 JSTの終了コード0と
  監視時刻の保存を確認しました。試験用タスクは削除済みです。本口座用の設置は口座準備後です。

次は全口座照合の未確認条件、発注経路との接続を進めます。ACK不明・FAULT区間の強制解除はありません。
継続同期の成功前に、同じ取得回と台帳末尾で残高・宣言済み建玉を照合する経路を追加しました。
指定した拘束・評価診断の不一致も永続停止します。開始建玉の宣言がない旧台帳は未確認として残し、
空の宣言と区別します。通知・期限切れ・別所有者・比較中の台帳変更・計上後の不一致を合成検証しました。
読取CLIでも宣言済み建玉の現在拘束をGETで照合します。予備口座・既知注文・最終口座・通知約定の取得は
共通の30秒予算で行います。未知・途中出現・意図不一致・未通知約定を拒否し、部分約定の計上後に
残りの拘束を照合する経路を合成検証しました。実口座の注文意図・開始境界・履歴完全性の証明ではありません。
実口座の長時間受入は未実施です。
発注とトークン操作で共有する[永続POST制御](post-control.md)を追加しました。GET制御に一つだけ紐付け、
現在の読取CLIでもトークン操作に使います。実プロセス終了後のclaim保持、1.1秒間隔、停止迂回の拒否を
合成検証しました。別プロセスの処理中検査と、登録表の欠落・書換えの拒否も確認しました。
照合失敗で受信終了がワーカー完了より先になっても、停止理由を`sync_failed`として保存します。
結果別の明示復旧は残っています。
[注文POSTの受付記録](order-receipts.md)を追加しました。公式仕様の3状態を保持し、受付で
約定や失効を確定しません。既存のオフライン台帳に保存し、後のGETとのID・状態の矛盾を停止します。
89件の試験で、実プロセスの受付commit前後の終了、再送拒否、GETとの接続、注文受付より古い約定の拒否を確認しました。
オフライン台帳は実口座へ昇格しません。[専用の実口座台帳と送信API](live-orders.md)を追加し、
初期無効・期限付きの運用者確認・共通POST所有権・待機後の口座リスク検査・送信直前の停止確認を接続しました。
55件の合成試験で新規・建玉指定決済、損失停止後の決済、署名・固定ホスト、通信・保存失敗、
4境界での実プロセス終了と非再送を確認しました。実口座を有効化した証拠ではありません。
完全な正規化口座証拠は信頼する供給側の責任です。読取診断を完全性フラグへ自動変換しません。
取消HTTP、注文結果別の復旧、資格情報・読取CLI・既知注文・監視との接続、コード更新時の移行、
口座本人性・業者条件・完全履歴の受入、戦略昇格と小額試行は残っています。
外部レビューで見つかったトークン失敗・共通POST枠の競合に対応し、操作別記録・最大3秒の待機・
失効後の明示復旧を追加しました。旧クライアントの再使用、注文・取消・明示停止・時計異常の解除を拒否します。
両タスク登録スクリプトのPlanOnly出力も修正し、日本語・空白のパスをコードページ932・UTF-8で
受け渡す4試験と既存Privateタスク9試験が合格しました。
通常終了は開始済みRESTの元の期限まで待つように修正しました。新しい取得を開始せず、
期限内に終わらないワーカーは停止と所有権を保持します。3件の追加試験を含む同期関連57件が合格しました。
REST先行・通知先行の構造や口座数値の不一致は、受信を継続して上限付きで再取得します。
保留中は成功と扱わず、約定内容・注文意図・保存物の矛盾は即時停止します。追加12件と拘束読取14件で
遅れた通知・明細が一致した後の一度だけの計上、回数または期限による停止を確認しました。
全履歴監査の費用、監視記録の保存上限、旧stream_bindingの欠落検出、所有権検査の一時競合、
paperタスクの所有者SID確認は残工程です。
旧version 1の上限は変わりません。新version 2とSupervisorは予定切替に対応しますが、
接続間に失った履歴を修復しません。差分取得でも未計上・部分約定の注文が多数ある場合の取得期限は残ります。

10月3日の追加実装は`codex/fx-practical-operations`ブランチで機能ごとにコミットしています。
実口座の読取受入と小額試行には口座準備が
必要ですが、長時間同期・全口座照合・発注の障害試験は口座なしで進められます。
