# 読み取り専用の口座データ取得・再生基盤

2026-09-30。[GMOコイン外国為替FX API仕様](https://api.coin.z.com/fxdocs/)を確認して実装。
**デモとテストには口座・APIキーは不要です。** 模擬応答／ローカルJSONの再生に加えて、
[明示認証情報を使うGET専用HTTPアダプター](private-read.md)を用意しました。
キー自動読込、実発注、自動売買への接続はなく、実口座での通信は未検証です。
既存ペーパー観測の固定コア、設定、DB、スケジュールは変更しません。

## 今回できたこと

- `/account/assets`、`/openPositions`、`/activeOrders` のGET要求と応答処理。
- 建玉・有効注文を `count` と `prevId` で走査。短いページでも空ページまで進み、
  重複ID、進まないカーソル、欠けたリスト、件数超過、ページ上限到達を拒否。
- 銘柄フィルターを付けずに取得し、別通貨の建玉・注文を隠さない。
  現在の対応はUSD/JPY、通常指値注文。STOP/OCO等、顧客注文IDなしの注文は拒否する。
- 各走査の前後に資産残高を取得し、さらに全走査を2回比較。
  残高・建玉・注文や未知の応答フィールドが変わった場合、その収集全体を拒否する。
  時価評価総額・余力・拘束証拠金・評価損益・証拠金維持率の変動は比較から除く。
  レポートの金額は最後の走査値を保存する（証拠金維持率は応答ハッシュの対象のみ）。
- 応答時刻・受信時刻・時計の逆行・取得時間上限を確認し、要求条件と応答JSONの
  正規化SHA-256を診断結果に記録する。生のサーバーエラーや通信例外は表示しない。
- 金額をDecimal、数量を整数、時刻をタイムゾーン付きとして正規化する。
  見込み手数料、評価損益、未決済スワップ、注文中建玉数量を別項目で保持する。
- 既知の注文IDについて `/orders` と `/executions` を2回読み、
  ID・注文条件・約定数量・価格保護・手数料の既存検証を適用する。
  約定ID重複、途中変化、注文不明を拒否する。空応答を注文拒否の証拠にしない。

## 意図的に許可しないこと

`AccountReadReport` は `AccountSnapshot` とは別の型です。
`traversal_exhausted=true` は走査末尾に達したこと、`repeated_state_equal=true` は
2回の構造比較が同じだったことだけを示します（時価項目の一致は含みません）。完全な口座証明でも発注許可でもありません。
発注ゲートへの変換関数、`complete=true` を自動設定する経路はありません。

結果には次の未確認条件が常に残ります。

| 条件 | 未解決の理由 |
| --- | --- |
| 口座本人性 | 確認したREST応答には口座IDがない。ローカルのラベルを本人性の証拠にしない |
| 同一時点の一貫性 | REST複数呼出の共通スナップショットIDは確認できない。2回同じでも間の変化・反映遅延を否定できない |
| 約定履歴の完全性 | 最新約定APIは最大100件で、履歴全体を証明しない。今回これを履歴復元に使わない |
| 証拠金・費用・丸め | 生の見込み手数料や余力を保存するが、既存口座ガードの数式との一致は実口座で未確認 |

`collect_order` の結果も `executions_complete=false` のままです。
有効注文の `size` は注文総数量として保存し、未約定残量として扱いません。
約定照合をせずに総数量を `WorkingOrder.remaining_units` へ移すことは禁止です。
注文IDを失った場合、顧客注文IDだけを使う完全な履歴検索は今回実装していません。

残高・評価損益等は符号付きで保持し、負の値をゼロに丸めたり、
`equity = balance + positionLossGain + totalSwap` を業者の確定仕様として仮定したりしません。
時価項目の変動だけでは拒否しません。残高・数量・価格・売買方向・注文内容・スワップ・
見込み手数料・未知の項目の変化は引き続き拒否します。除外する金額も各応答で形式を検証します。
これは発注用途の一貫性保証を実装したという意味ではありません。

## 口座なしのデモ

```powershell
uv run python -m trading.account_read_lab demo --directory runs/account-reader-demo
uv run python -m trading.account_read_lab replay --input runs/account-reader-demo/transcript.json
```

未使用の出力ディレクトリを指定してください。既存ディレクトリは上書きしません。
デモは「1,000通貨の注文に対して400通貨を保有している合成データ」を12回のGET応答として再生し、
`transcript.json` と `report.json` を作ります。数値は業者条件・実口座値ではありません。
残り600通貨の注文が確実に存在するという判定までは行いません。
`replay` はファイルを変更せず、正規化した診断結果を標準出力に出します。

再生JSONの形式は `started_at` と `exchanges`。
各exchangeは `method: "GET"`、`path`、`query`（キー・値ペア）、`received_at`、`response` を持ちます。
要求順序・パラメータが一致しない場合、途中で応答が不足する場合、余った応答がある場合は拒否します。
再生には実時計でなく記録した受信時刻を使うため、同じファイルを後日も検証できます。
入力は2MBまで。将来実口座の記録を扱う場合は口座情報として保護し、Gitへ追加しないでください。
秘密鍵や認証ヘッダーをtranscriptに入れてはいけません。

## 次の実装と実口座が必要な確認

1. GET専用HTTP、タイムアウト、同一プロセス内の共有リミッター、自動リトライしない方針は
   [実装済み](private-read.md)。同じローカルDBを使う[プロセス間制限・停止の永続化](read-control.md)も追加。
   [Windowsキー保管](credential-store.md)は模擬検証まで追加。
   [未完了claimのない一部状態の手動復旧](read-recovery.md)も追加。
   version 3では[OSロックで所有者不在を確認するclaim解消](read-orphan.md)も追加。
   実ストア受入確認、別PC／他アプリとの制御、旧版claimの移行は未完了。
2. [変更通知とRESTの構造照合・再取得基盤](account-sync.md)をオフラインで追加。
   ローカル受信列の欠番・切断・通知中の取得結果の拒否・再接続時の世代分離を検証済み。
   実WebSocket接続、口座／キーの紐付け、業者側の欠落の完全検出、約定の会計照合は未完了。
3. 口座開設後の読み取り専用検証。手数料・スワップ・丸め、
   外部操作・入出金・既存建玉、消失した注文IDを扱う条件を確認する。
4. その証拠を満たしてから口座ガードへ接続する。実送信、送信直前の再検査、
   緊急停止／再開、実資金上限は別工程。戦略の収益性承認も別に必要。

テストの成功は模擬入力に対する検証で、実APIとの接続成功や実運用の承認ではありません。

## 2026-10-01 検証条件の補足

金額・数量はASCIIの十進文字列、業者時刻はタイムゾーン付きISO日時文字列に限定します。
数値のUnix時刻や全角数字を暗黙変換しません。`collect_order` の約定観測時刻には
最後のREST応答時刻を使い、初回注文応答の直後に発生した約定も正しく検証します。

`AccountReader(..., clock_skew_ms=100)` のように、業者時刻がローカル受信時刻より未来に
なる許容幅を明示設定できます。整数0〜1,000ms、既定0msです。実測に基づく調整が必要で、
100msは例示です。古い応答の上限、ローカル時計の逆行、収集期限は緩和しません。

0件応答が `data: {}` になるかはFX実APIで未確認です。現時点では `data.list: []` だけを
走査終了とし、空辞書は引き続き拒否します。読み取り専用の受入で、建玉・有効注文・
既知注文の約定が0件の場合の応答を確認してから受理形式を追加してください。
