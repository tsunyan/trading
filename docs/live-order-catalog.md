# 発注台帳から読取同期への注文登録

2026-10-04。同じGET・POST制御に紐付いた専用実口座台帳の注文を、Private同期の追記専用
カタログへ登録する経路を追加しました。同期開始前と注文GETの前に保存済みの受付・照合を検査し、
業者注文IDと元の注文意図を登録します。稼働中に受け付けた注文も、次の読取で追跡できます。
実口座は未準備で、検証は模擬HTTP・ソケット・資格情報ストアと一時DBで行っています。

## 登録元と検査

同期設定に別の発注台帳のパスを追加しません。元のGET制御に永久登録されたPOST制御と、
そのPOST制御に永久登録された`live-execution-v1`台帳を使います。
GET・POST・台帳の識別子、scope、保存場所、同期カタログの紐付けを検査します。
凍結した`sync-plan.json`、paper DB、観測設定を変更しません。

各注文では、元の準備要求、送信を一度だけ消費した履歴、その後の受付または保存済みGET照合を
検査します。受付と照合が両方ある場合は意図・親注文ID・注文ID・時刻の一致も要求します。
業者IDを含む検査済み受付か照合が必要で、準備だけの注文や未送信の放棄注文は登録しません。
結果不明で業者IDが保存されていない注文は`unidentified_client_ids`に残し、IDを推測しません。
完全な終端結果に限らず、履歴不完全の証拠もID対応だけに使えます。完全性フラグは変更しません。

カタログには元の注文意図と業者注文IDを保存し、`source_ref`に台帳識別子と元証拠のSHA-256を
記録します。同じ対応の再登録は件数を増やさず、別の意図やIDとの競合は上書きしません。
通常の同時追記で末尾が変わった場合は最大3回読み直します。上限は既存カタログと同じです。
既存の対応はまとめて検査し、新しい対応だけを追記します。各登録済み注文について毎回
カタログ全量を読み直す処理は避けます。履歴全量の読取り・検証と保存量は件数に比例して残ります。
複数注文の登録途中で終了した場合は、確定した対応を保持し、残りを次回に登録します。
保存済み受付を再送したり、未解決POST claimや停止を解除したりする操作ではありません。

## 実行

カタログを持つ現在形式の同期環境では、`private_sync run`と`reconcile-stopped`が自動使用します。
元のPOST制御に発注台帳が紐付いていなければ、従来の手動登録を使います。
紐付いた発注台帳がある旧同期環境では、先に[カタログの明示移行](private-sync.md)が必要です。
紐付け済みの保存物が欠落・破損した場合は、作り直さず拒否します。

通信なしで登録だけを実行する場合は、`status`で固定設定とカタログ末尾を確認します。

```powershell
uv run python -m trading.private_sync status --directory runs/private-sync
uv run python -m trading.private_sync register-live-orders --directory runs/private-sync --expected-plan-sha256 <plan_sha256> --expected-catalog-head <catalog.head>
```

このコマンドは開始時の設定・末尾を検査し、資格情報の読込・HTTP・計上・発注・有効化を行いません。
保存済みの対応を使うため、新しい意図を手入力して確認する操作もありません。
同期・POST・台帳が停止中でも、元の紐付けと証拠が有効なら登録だけを実行でき、停止を保持します。
古い手動checkpointの拒否では発注台帳を新たに停止しません。

## 取得・計上と停止

同期開始時はネイティブ資格情報の読込より先に登録元を検査します。
各注文のGETではID対応を更新し、取得後も最新の保存済み受付・照合と結果を比較します。
受付より古い証拠、別ID、意図不一致、消えた・変わった過去約定、確定済み終端履歴の変更を拒否します。
全口座・注文取得の共通期限には、ローカルの登録・取得後検査も含めます。
整合する約定は従来のWS/REST照合から現金・宣言済み建玉の台帳へ一度だけ計上します。

登録元の不正、カタログの競合、未知の業者ID、受付・履歴とGETの矛盾では発注台帳も停止します。
紐付いた同期実行が失敗してSTOPPEDになった場合と、読取クライアントの後片付けが失敗した場合も
発注台帳を停止します。正常終了・予定切替は既存の許可を更新しません。
通常のPOST送信ではGETが使用中なら従来の事前検査が拒否します。読取の所有権を迂回しません。
プロセス自体が終了した場合の発注停止への反映と独立監視の接続は、引き続き残工程です。

この経路は発注台帳の注文状態や完全な口座リスク証拠を自動更新しません。
読取診断の`complete=false`や`executions_complete=false`を完全性の証明へ昇格させず、
同期の成功を発注許可へ変換しません。注文状態の更新、claim解消、[明示再開](order-restart.md)は
保存済み証拠と既存の手続きを使います。
完全な履歴・口座証拠の供給、発注側の状態・リスク更新、資格情報ストアから発注クライアントへの
接続、独立監視、戦略昇格と実口座受入は残っています。

## 検証

`tests/test_live_order_catalog.py`で、受付とGET証拠のID登録、元の準備・送信・受付・照合の欠落/改変、
意図とIDの競合、時刻・過去約定・確定履歴の矛盾、コード更新、結果不明claimの保持を検証します。
実際の模擬注文POSTから、稼働中の自動登録・GET照合・現金と建玉の照合まで接続しました。
停止中の部分約定も一度だけ計上し、全制御の停止と旧許可を保持します。
登録前後で実プロセスを終了させ、再実行による重複登録の拒否を確認しました。
追加46試験を含む全2138テストとRuffの検査・整形確認、差分チェックが合格しました。
実口座への通信、実資格情報の読込、Windowsタスク変更は行っていません。
