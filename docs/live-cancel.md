# 実口座台帳に紐付いた注文の取消

2026-10-04。`PrivateOrderClient.cancel(client_id)`を専用台帳と永続POST制御へ接続しました。
単一USD/JPYの通常注文について、新規・建玉指定決済、部分約定した残注文を対象にできます。
実口座は未準備のため、検証は一時DB・合成HTTPとGET・実プロセスの途中終了で行っています。

## 取消対象と許可

既存の`LiveOrderJournal`と、その台帳に永久登録したPOST制御を使います。
発注と同じ期限付きの有効化、現在コードの識別子、元のGET制御の使用可能状態を確認します。
通常の経路は停止・許可失効・コード変更で送信を拒否します。
対象を指定した明示的な取消許可は、下記の別手続きで保存します。
キーの自動読込、CLI発注、一括検索による全注文取消はありません。

取消前に、保存済み注文が`WORKING`、`PARTIAL`、またはGET証拠を持つ`RECONCILING`であることを
確認します。未送信、受付のみ、対象ID不明、終端状態、取消要求済みでは拒否します。
準備・送信履歴、受付記録、最新の照合履歴と保存証拠の一致を検査し、業者の親注文IDを選びます。
証拠の鮮度上限には既存の`AccountPolicy.max_snapshot_age_seconds`を使用し、既定は60秒です。

GET証拠の`executions_complete=false`を完全性の証明へ変換せず、そのまま取消に使えます。
この操作は新しい注文を作らないため、新規発注用の気配・最新全口座証拠を要求しません。
損失による新規停止`entry_halted`も保持したまま取消できます。注文・現金・建玉の予約を
取消受付だけで解放しません。口座全体の不整合や明示停止では通常の送信を許可しません。

## 停止を保持した対象限定の取消許可

`cancel_context(client_id)`で、対象注文、GET証拠、台帳の識別子・許可・停止・口座ゲート、
現在コード、履歴末尾、POST世代と本文を含むcheckpoint SHA-256を確認します。
この取得はローカルのみで、資格情報や通信を使いません。
`authorize_cancel`は口座本人性・業者条件・読取受入の参照とSHA-256、確認事項、
期限付きの`CancelApproval`を受け取り、`CANCEL_AUTHORIZED`をcommitします。
参照は運用者が確認した証拠であり、コードが口座本人性を自動証明するものではありません。

```python
from trading.live_journal import CancelApproval

context = journal.cancel_context(client_id)
approval = CancelApproval(
    account_id=context["account_id"],
    checkpoint_sha256=context["checkpoint_sha256"],
    accepted_at=accepted_at,  # timezone付きdatetime
    expires_at=expires_at,  # accepted_atから最大10分
    evidence=verified_cancel_evidence,  # identity / rules / read_acceptanceを各一件
)
permission = journal.authorize_cancel(
    client_id,
    approval,
    confirmations={
        "cancel-only",
        "account-identity",
        "broker-rules",
        "read-acceptance",
        "external-writers-paused",
        "preserve-stops",
    },
)
receipt = client.cancel(client_id, authorization_sha256=permission)
```

この許可で`STOPPED`の台帳、期限切れ・コード更新後の通常許可に紐付いた残注文を取消できます。
台帳の停止、旧発注許可、損失停止、口座証拠、消費済み送信を保持し、新規・決済の許可は更新しません。
口座全体が未確認でも、対象の正しい業者IDと履歴、鮮度は通常取消と同じ基準で検査します。
GET制御が停止中、POSTが停止中・使用中・結果不明なら許可を保存・送信できません。
未解決POST claimを解放して取消する経路ではありません。

送信前、1.1秒の待機後、HTTP直前に同じ許可を検査します。許可保存以降の照合・口座更新・
緊急停止・コード変更・別POST操作・新たな取消許可は古い許可を無効にします。
GET証拠の鮮度期限も維持し、長い許可期限で延長しません。
変更があればcontextを取得し直し、証拠を確認して改めて許可します。
取消claimを消費した後は、再承認しても同じ注文を再送できません。
送信後に許可失効や緊急停止が起きても、正しい受付記録は保存して停止を維持します。
未使用の許可は再起動後も保存済みcheckpointを検査して使えます。自動送信は行いません。

## 送信と受付

[GMO公式の注文取消](https://api.coin.z.com/fxdocs/#cancel-orders)に従い、保存証拠の親注文IDを
一つだけ`rootOrderIds`へ入れ、`POST /v1/cancelOrders`へ送ります。
共通POST所有権・要求SHA-256をcommitし、1.1秒待った後、許可と対象の鮮度を再検査します。
同じtransactionで`CANCEL_PENDING`と`CANCEL_CLAIMED`を保存してからHTTPに入ります。
取消claimはPOST claim、親注文ID・注文ID、元のGET証拠のハッシュを保持します。
最終送信検査でも所有者・claim・コード・対象・本文を確認します。

同じSDKオブジェクトや別プロセスの同時送信を拒否します。一つのローカル注文につき、
取消送信の試行を一度だけ消費します。注文行の状態だけを戻しても履歴が再送を拒否します。
待機後の許可失効や証拠期限切れなど、取消claimを消費する前の確定した拒否ではHTTPを送らず、
POSTの待機枠だけ正常完了します。元の注文を維持し、取消claimを消費しません。

取消claimの後、HTTPクライアントに要求を渡す前に拒否された場合（送信直前の再確認・健全性検査・1秒の期限）は、
業者へ何も送っていないことが確実です。`CANCEL_NOT_SENT`（固定の理由コードと戻す状態）を記録し、注文を
証拠どおりの`WORKING`または`PARTIAL`に戻して、POST枠を正常完了します（`cancel_not_sent:<理由>`）。
消費したclaimは履歴に残り、対象限定の許可も使用済みになります。次の取消には新しいclaim（と許可）が必要です。
claimと`CANCEL_NOT_SENT`は交互にしか並ばず、送った（または送ったかもしれない）claimは開いたまま残って、
以後の取消を拒否します。記録に失敗した場合と要求を渡した後の失敗は、従来どおり結果不明です
（2026-10-05の再レビューR9）。

公式応答の`data.success`は取消受付の成功を表します。対象の親注文IDと顧客注文IDが一致する
一件の応答だけを`CancellationReceipt`として保存します。空結果・別対象・重複キー・非成功・
想定外の項目・時刻不整合は、未取消と推測せず結果不明にします。
保存するのは対象ID、開始・応答・受信時刻、SHA-256です。生の応答やキーを保存しません。
HTTPの固定ホスト・TLS・無再試行・期限・サイズ制限と認証情報の後片付けは発注と共通です。

受付記録の保存後だけPOST枠を正常完了します。保存前後のコード変更や緊急停止があっても、
既に受け取った有効な受付を保存できます。これによって旧許可や停止を解除しません。
通信・受付解析・保存・後片付けが不明なら、取消claimを保持し、注文を`UNKNOWN`、
実口座台帳とPOST制御を停止します。再送やトークン限定復旧では解消しません。

## GET照合と結果不明の調査

取消受付後も`CANCEL_PENDING`を保持します。部分約定したままの応答、同じ有効注文、
履歴不完全な取消・約定状態では予約を解放しません。
独立した証拠で履歴完全性が確認された後、取消・失効・全量約定へ進めます。
取消と全量約定が競合した場合は、約定を取消として処理しません。

中断した取消は[GET照合CLI](order-recovery.md)で調べられます。
元の注文の業者IDを指定し、取消claim・要求ハッシュ・元の証拠を含むcontextを確認します。
後続GETで部分約定が増えても、取消を開始した時点の証拠を履歴から検証します。
調査後もPOST claimと停止を保持します。[終端結果のclaim解消](order-resolution.md)は、
別に確立した完全な終端証拠・全口座照合・明示確認を要求します。
[停止後の明示再開](order-restart.md)は未解決claimがなく、完全な注文・口座照合と新しい確認が
揃った場合に使えます。後片付け失敗後も、完全に照合した残注文を再開後に取消できます。
有効なまま残る取消結果不明は[専用観測と承認によるclaim解消](order-resolution.md)で扱います。
取消の成否は不明のまま保持し、同じ取消の再送は永久に拒否します。通常の口座ゲートと停止も保持します。
