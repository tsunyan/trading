# 旧所有権・欠損した所有物の復旧に必要な証拠

2026-10-05。旧GETの未完了claim、欠損したOS所有権ファイル、移行中に作成された未記録のファイルは、
現在の復旧CLIでは解消できません。この文書は、その残件を実装する前に必要な資料と判定条件を定めます。
復旧の承認や実行手順ではありません。資料を揃えても、停止解除・注文再送・口座本人性の確認にはなりません。

## 現在使える手続きと未提供の境界

| 保存状態 | 現在の手続き | 残る条件 |
| --- | --- | --- |
| version 3の未完了GET、元の所有権ファイルが健全 | [GET claimの明示解消](read-orphan.md) | 元の同じファイルでOS所有権を取得し、対象claimと監査末尾を再検査する |
| version 1/2、停止済み、未完了GETなし | [停止を保つ現形式移行](read-owner-upgrade.md) | 旧クライアントを終了し、元の識別子・保存先・紐付けを保持する |
| 移行開始がcommit済み、所有権ファイルはまだない | 同じページの`complete` | 保存済み判断のSHA-256、元の状態と監査末尾が不変であること |
| version 1/2の未完了GET | 未提供 | 当時の所有者と起動経路、関連処理の終了を確認する外部資料が必要 |
| version 3または同期制御の所有権ファイルが欠損・差替え | 未提供 | DBに保存した元のファイル識別子に対する所有権証明を、新しいファイルで代用しない |
| 移行開始後、ファイル作成済み・DBのowner identityは未記録 | 未提供 | ファイルの内容一致だけで採用しない。作成した処理と保存境界を別途確認する |
| 元の同期所有物が健全で、ACK不明・FAULT区間が残る | [受渡し確認・停止中の照合・復旧](private-sync.md) | 不明を維持して確認を記録し、保存済み約定をGETと照合して計上する |

同期のACK不明は、旧GETの所有者不明と別の問題です。同期の確認が済んでも、未完了GETや欠損したロックは
解除しません。新しいディレクトリ・別のscope・新しい同期環境で元の停止を迂回することもできません。

## 元の制御へ結び付ける資料

一つの調査記録に次の関係を残します。各資料には取得日時・取得元・ファイルのSHA-256を付け、
値が分からなければ「不明」と記録します。後から推測で埋めません。SHA-256は資料の同一性の照合用で、
取得元の正しさ、悪意ある改変や過去への巻戻し、業者口座の本人性を証明するものではありません。

| 資料 | 結び付ける値 | 欠けた場合の判定 |
| --- | --- | --- |
| GET制御 | 元の絶対ディレクトリ、scope、version、instance、停止理由、対象claim、監査末尾 | 対象を確定できない |
| POSTと同期の紐付け | GET側の登録と監査履歴、POSTのinstanceと保存先、同期instanceと設定SHA-256 | 別環境への差替えを否定できない |
| 同期保存物 | controlのrevision・generation・phase、journalのseries・instance・head、cashのinstance、catalogと監視の登録 | 元の計上・監視対象を確定できない |
| 所有権ファイル | DBに保存したdevice/inode、現在のパスと実ファイルの識別子・種別・サイズ | 元の排他領域の健全性を確認できない |
| 起動元の資料 | PC、実行アカウントのSID、元のタスク・サービス・手動起動、実行ファイルとコード版、引数と保存先、自動再起動の設定 | 関連する起動経路を列挙できない |
| 終了と再起動停止の資料 | 列挙した各起動元について、対象プロセスを識別する起動時刻と終了記録、自動再起動停止の記録 | 現在も元の処理が動ける可能性を排除できない |
| 通信・計上の境界 | GET/POSTの別、通知受渡しの不明、保存済み約定と計上済みreceipt、トークン終了の不明 | GET解消を注文・通知・会計の成功へ読み替えられない |

PIDが見つからないこと、時間経過、タスクが現在止まって見えること、新しく作ったロックの取得成功だけでは、
旧GETの元所有者不在を証明できません。旧GETは通信中にOSロックを保持していませんでした。
現在のコードで初めて作った証拠を、過去のclaim取得時の所有権証拠として扱いません。
元の起動経路を列挙できない場合は、資料不足として停止を保持します。

同一PC・同一ローカル制御を使う協調プロセスの範囲を明記します。別PC・別DB・他アプリは、現在の
OS所有権プロトコルの保証範囲外です。業者側の処理終了は、ローカルの所有者不在とは別に扱います。

資格情報、署名ヘッダー、通知トークン、生の例外本文は調査記録に含めません。必要な既存ログを保全する場合も、
共有用の資料には識別子と必要な境界情報だけを転記します。この文書のために実キーを読んだり通信したりする必要はありません。

## 状態確認が拒否された場合

正常に開ける元の制御では、[GET状態](read-control.md)・[移行状態](read-owner-upgrade.md)・
[同期状態](private-sync.md)を使って現在値を確認できます。これらは証拠一式を作る専用の読取専用採取機能ではなく、
複数ストアを同時刻に固定する機能もありません。復旧の承認時には対象の状態を検査し直します。

欠損・差替えで状態CLI自体が拒否した場合は、その固定理由と元の保存物を保全します。状態を表示するために
ロックを作り直したり、DBを編集・差し戻したり、別の制御へ登録したりしません。
DBとロックのコピーは調査用の保存物であり、元の排他領域を復元した証明にはなりません。
GET・同期制御には、欠損時にも使える以下の読取専用の証拠採取を追加しました。タスク・起動元の
証拠を一括採取する機能と、欠損した所有物を修復する機能は未実装です。

## GET制御の証拠採取

```powershell
uv run python -m trading.read_control_evidence --directory runs/account-read-control --scope operator-account --output research/get-control-evidence.json
```

元のGET制御をファイルとして読み、一時ディレクトリへコピーします。SQLiteで開くのは一時コピーだけで、
読取専用・immutable・query-onlyに固定します。元のDBに索引を追加せず、ロックや表を作りません。
コピー前後のファイル識別子・サイズ・更新時刻と全バイトのSHA-256を照合し、採取中の変化を拒否します。
rollback形式のDBのみが対象です。journal・WAL・SHMがある場合、WAL形式のヘッダー、非通常ファイル、
256MiBを超えるDBは拒否します。関連処理を終了して静止した保存物を採取する工程で、稼働中のDB採取を保証しません。

出力は制御状態、GET側のPOST/同期binding、DBに記録したowner identity、直近20件の監査記録、
保存済み移行判断の指紋、所有権ファイルの現物情報です。表は最大2行、各フィールドはUTF-8で64KB以下に限ります。
監査の任意payloadと移行判断の本文は出力せず、指紋を残します。claimなどの32/64桁の16進識別子だけは表示します。
POST/同期bindingの識別子は32桁の小文字16進数、ownerのdevice/inodeは数字列として検査し、
任意文字列や不正な行数・idは`read_evidence_metadata_shape_invalid`で拒否します。
旧形式・欠損調査のため、optionalな表の不在・空はそのまま記録します。POSTのパスは絶対パスの形式だけを
検査し、紐付け先を解決・参照しません。表の形式検査は、bindingの監査履歴や保存先の健全性を保証しません。
監査のid・wall_nsと移行判断のidも整数に限り、不正な文字列をそのまま表示しません。
所有権ファイルが欠損していても再作成せず、存在する通常ファイルは32バイトの現物と識別子を採取します。

JSONの`sha256`は、`payload`をキー順・空白なしの標準JSONで符号化したUTF-8本文の指紋です。
元DBの指紋は`payload.source.sha256`に別に保存します。取得日時を含むので、同じDBの再採取でも
資料全体の指紋は変わります。既存の出力は上書きせず、元のGETディレクトリ内への出力も拒否します。
出力先の親ディレクトリは先に存在している必要があります。`--output`を省略すると標準出力へ表示します。

表・履歴は`unverified`として扱い、末尾20件は全claim履歴の検証ではありません。
コピーのSQLite構造検査とバイト一致も、保存内容の正当性や過去の巻戻しを証明しません。
`owner_absence_established=false`、`recovery_authorized=false`、`history_complete=false`を常に記録します。
OS所有権を取得せず、起動元・実行中処理・SID・業者側の処理終了を調査しません。
複数ストアと所有権ファイルを同時刻に固定する機能もなく、承認に使う状態は別途検査し直す必要があります。

検証は元DB不変更、SQLite接続がコピーのみであること、旧未完了claim・欠損した所有物の保持、
任意payloadの非表示、WAL/sidecar・採取中の更新・過大入力・別scope・不正schemaの拒否、
既存出力と元の保存先の保護を、一時保存物で行います。実口座・実資格情報・実タスクには使用していません。

## 同期制御の証拠採取

```powershell
uv run python -m trading.stream_control_evidence --directory runs/account-sync/control --scope operator-account --output research/stream-control-evidence.json
```

GETと同じコピー方式・容量上限・sidecar拒否・全バイトの前後照合を使い、元の`stream-control.sqlite`を
SQLiteで開きません。OS所有権を取得せず、journal・cash・catalog・監視ストアも開きません。
DBに保存されたjournal/cashのパスと識別子は、紐付けの調査用に表示するだけです。
それらの保存先が欠損していても作り直さず、実在・健全性・会計との一致を保証しません。

出力は`control_unverified.state_unverified`に保存状態、`audit_tail_unverified`に直近20件の遷移を記録します。
状態は既存の`ControlState`形式とscopeを検査し、不正なJSON・未知フィールド・不整合なphaseなどを拒否します。
元のbodyは表示せずSHA-256を保存し、`digest_matches_body`と`body_matches_canonical_state`で
DB内のdigestとの一致と標準形式への一致を個別に示します。digestが欠損・不正なら一致はfalseです。
形式検査や一致がtrueでも、全遷移・関連ストア・過去への巻戻しを検証した意味にはなりません。

所有権ファイルの`identity_matches_control`は現在のdevice/inodeと保存値の比較、
`contents_match_instance`は32バイトの現物と同期instanceの比較だけです。欠損・不正サイズなら
前者はfalseです。内容が一致する差替えファイルも、元の所有権の代替として採用しません。
`owner_absence_established=false`、`recovery_authorized=false`、`history_complete=false`、
`cross_store_atomic_snapshot=false`を常に記録します。RUNNING・cleanup_unknown・停止理由を保持します。

Windowsでは既存所有者が保持するロックのバイト読取り自体が拒否される場合があります。その場合も
所有権を取得・解除せず、固定理由で採取を拒否します。関連処理を終了して静止した保存物を採取する工程です。
GETと同様、出力は元の制御ディレクトリ外に限り、既存ファイルを上書きしません。
JSON全体の指紋の計算方法と採取結果の限界もGETと同じです。

検証は欠損・差替え・不正内容の所有物、残るRUNNING状態、関連ストア欠損、採取中の更新、
WAL/sidecar、過大入力、不正body/digest/schema/遷移、末尾20件の上限、出力先保護を一時保存物で行います。
実口座・実資格情報・実タスクの資料採取ではありません。

## 将来の復旧実装に課す条件

旧claimの解消と所有物の修復を一つの汎用resetにまとめず、対象と保存境界ごとに契約を定めます。
外部資料の存在を確認するだけで承認せず、どの資料がどの元所有者・起動元・bindingを証明するかをレビューします。
歴史的な証拠を再構成できないケースには、資料不足で拒否する結果が必要です。

実装する場合は、元の制御の識別子・claim・停止理由・binding・監査末尾と資料の指紋を期限付き提案に結び付けます。
承認前に状態変更・新しい停止・時計異常・期限切れを再検査し、並行承認を単回に制限します。
既存のOS所有権証明が使える場合は、それを取得してから保存を確定するまで排他を保持します。
旧形式に存在しなかった証明の代替が必要な場合は、その保証範囲と不足条件を先に設計・レビューします。

確定するのは指定したローカルclaimまたは保存済み判断の完了だけです。停止、取消の再送禁止、POSTの不明、
通知受渡しの不明、口座・会計の通常ゲートを維持し、GET・同期・実発注の再開は既存の別手続きに残します。
実装SHA-256が変われば実発注の既存承認も再確認が必要です。

保存前・保存途中・commit後の別プロセス終了、所有者の競合、資料とbindingの差替え、監査の変更、
時計異常・期限切れ、SQLite busy・I/O失敗、並行承認、停止保持を一時保存物で検証することを完了条件にします。
欠損した所有物・未記録のファイル・資料不足を正常終了へ変換する試験結果は受理しません。
実口座・実タスクでの受入は、こうした開発試験とは別の工程です。
