# 約定の永続現金会計

2026-10-02。`ExecutionCashBook` を追加しました。
個別の約定通知と既知注文のREST証拠を再照合し、損益・支払手数料・決済スワップを
専用SQLiteへ一度だけ計上します。ペーパーDB・注文台帳・通知ジャーナルとは別の保存先です。
[開始建玉を宣言した建玉会計](execution-positions.md)も追加しました。
[明細証拠による入出金会計](cash-transfers.md)も追加しました。
実口座接続、送金、発注ゲートへの変換は行いません。

## 初期残高と対象期間

新規作成時に、ローカルの `scope`、円建ての開始残高、対象期間の境界 `cutoff` を明示します。
約定日時が境界より後の約定だけを受け付け、同時刻やそれ以前は拒否します。
開始残高を、取込予定の約定を既に含む現在のREST残高から自動で作る処理はありません。

これは運用者が宣言した計算の開始点です。残高にどの約定が既に含まれているか、
その時刻で口座が原子的に固定されたか、scopeが実口座本人性と一致するかは未証明です。
実口座での初期残高と履歴の境界確認は別途必要です。

```python
from datetime import UTC, datetime
from pathlib import Path

from trading.execution_cash_book import ExecutionCashBatch, ExecutionCashBook, OpeningCash

book = ExecutionCashBook.create(
    Path("runs/my-cash-book"),
    "declared-account-scope",
    OpeningCash(balance="1000000", cutoff=datetime(2026, 10, 2, tzinfo=UTC)),
)
# notices はparse_eventで解析した約定通知。
# reports は元の注文意図と既知注文IDを使ってAccountReader.collect_orderで取得した結果。
result = book.apply(ExecutionCashBatch(events=notices, reports=reports))
```

`create` は未使用ディレクトリだけを使います。
既存の台帳は `ExecutionCashBook(directory, scope)` で開き直します。
データベースが欠損・破損しても再作成しません。開始残高の上書きや自動リセットもありません。

## 約定単位の計上

[約定照合](execution-reconciliation.md)を再実行し、入力通知の全件が一致した場合だけ進みます。
通知がないREST約定は証拠に保持しますが、計上対象へ自動追加しません。
一致した部分だけを不一致バッチから取り込む処理もありません。
RESTの要求パス・注文ID・4回の観測順・時刻・応答ハッシュ形式を検査します。
過去の個別約定は後から照合できるため、この会計APIは現在時刻に対する観測鮮度を要求しません。
過去のREST証拠を現在の口座状態や発注許可へ昇格させるものではありません。
[同期モニターからの現金計上](execution-cash-sync.md)も追加しました。
捕捉アダプターへ台帳を明示すると、現在の世代・revision・鮮度を検査して個別証拠を渡します。

`ExecutionCashBatch(..., clock_skew_ms=100)` のように、業者応答時刻の許容差を明示できます。
整数0〜1,000ms、既定0msです。Readerと同じ実測に基づく値を指定し、保存した証拠と
再オープン時の検査にもその値を使います。100msは運用上の校正値ではありません。

各約定の金額は、既存パーサーの正規化済みの値を使います。
支払手数料は非負のdebitで、現金増減は `loss_gain - fee + settled_swap` です。
価格や取引元本、未実現損益、未決済の累積スワップ、証拠金・余力は現金へ加算しません。
決済損益の独自再計算や、業者の丸めの推定もしません。

次の4つの符号付き仕訳を、1約定について同時に保存します。正は借方、負は貸方です。
新規の支払手数料2円、決済損益40円・手数料2円・スワップ3円の例は次のとおりです。

| 勘定 | 計算 | 新規 | 決済 |
| --- | --- | ---: | ---: |
| `cash` | 損益 − 手数料 + スワップ | -2 | 41 |
| `realized_pnl` | −損益 | 0 | -40 |
| `fee_expense` | 手数料 | 2 | 2 |
| `settled_swap` | −スワップ | 0 | -3 |
| 合計 | 0 | 0 | 0 |

開始残高は `cash` と逆符号の `opening_equity` で保存します。
金額は小数8桁までの固定精度を整数に変換して処理し、浮動小数点や呼出側のDecimal精度に依存しません。
余分な末尾の0は許容します。8桁を超える端数は丸めず拒否します。
各金額と会計合計の絶対値は10^18円までです。この範囲はローカル実装の制限で、業者の商品ルールではありません。

## 一度だけの反映と競合

約定IDをデータベース内で一意にし、次を同じ `BEGIN IMMEDIATE` トランザクションでcommitします。

1. 約定ID、注文意図・注文ID・建玉ID・数量・価格・金額内訳・約定日時。
2. そのバッチのうち、今回新しく計上する約定の正規化済み通知と、その注文のREST観測証拠。
3. 4つの仕訳、記録件数、証拠の件数、末尾ハッシュ。

同期モニターのバッチは、接続以降の通知と注文をすべて含みます。これを毎回そのまま保存すると、
保存量が1接続の約定数の2乗で増え、約170件で本文合計の上限に達していました。
既計上との矛盾・欠損の検査は入力されたバッチ全体で行い、保存する証拠だけを今回の約定分に絞ります。

commit前の失敗は全体をrollbackします。commit後に結果を返す前に停止しても、再入力は既計上として扱います。
別プロセス・別インスタンスから同じ約定を入力しても、この同じDB内では一度しか増えません。
別DBを作ることや、整合した古いバックアップへ戻すことまで防ぐものではありません。

再配信や再照合は、約定IDだけでなく経済的な内容を比較します。
金額の文字列表現、通知ハッシュ、注文日時、累積約定数量、RESTの観測時刻が変わっただけなら
新しい計上にはなりません。ただし今回入力された通知とRESTが一致している必要があります。

既計上の約定内容、同じ注文IDの元の注文意図・親ID、顧客注文IDと注文IDの対応が変わった場合は、
最後の整合した残高を保持して `cash_book_identity_conflict` を永続記録します。
再起動後も `cash_book_halted` となり、追加計上を拒否します。自動解除はありません。
今回のRESTから既計上の同じ注文の約定が消えた場合も、後続の計上を拒否します。
こちらは証拠不足として扱い、矛盾の確定による永続停止とは区別します。

`apply` の `cash_delta` は今回新しく計上した約定だけの差分です。
`applied_execution_ids` と `already_applied_execution_ids` を分けて返します。
`accounting_applied=true` は、このバッチの個別約定をこの現金台帳へ反映済みという意味です。
照合モニターや通知ジャーナルの状態を変更するものではなく、全口座会計の完了も意味しません。
従来の照合集計値や `matched_cash_amount` を渡して加算するAPIはありません。

## 残高との比較

```python
comparison = book.compare_balance(reader.collect_account())
```

開始残高・既計上約定・明示した入出金から求めた残高を、REST資産の `balance` と比較します。
最新の既計上約定または入出金より古い観測は拒否し、金額差・観測残高・計算残高を返します。
必要なら `clock_skew_ms` をReaderと同じ値で明示します。
差があっても補正仕訳・入金扱い・自動停止解除は行いません。
比較は非永続の診断で、比較中の後続計上後も参照できるように対象の末尾ハッシュを含めます。

一致しても `complete=false`、`live_enabled=false` です。
履歴完全性・開始残高の境界・全入出金・外部操作・初期建玉・費用丸め・口座本人性・原子的な同期の
未確認条件を残します。現在のREST観測の鮮度確認や、後続通知による観測の無効化は、
従来のReader／同期モニターで引き続き行う必要があります。

## 保存の検査と上限

専用の `execution-cash.sqlite` を使い、書込みは `synchronous=FULL` で行います。
読み取りも書込み可能モードで開きますが、書込みはしません。書込み中のプロセス停止で残った
ロールバックジャーナルは、書込み可能な接続でしか戻せないためです。
各操作で、scope・DB識別子・開始残高・連続記録番号・証拠・ハッシュ連鎖・仕訳を再検査します。
建玉会計を明示したversion 2／3では、開始建玉・取得原価・決済損益も再検査します。
入出金を明示したversion 3では、資料証拠・3つの入出金仕訳も再検査します。
現金の合計だけでなく、すべての仕訳が元の個別約定に一致し、借方貸方の合計が0になることを確認します。
ハッシュは不整合検出用で、署名や悪意あるDB編集への防御ではありません。

既定の上限は5,000約定、新規作成時に1〜5,000件を指定できます。version 3は入出金と共有します。
1バッチは最大2,000通知・1,000注文レポート・REST約定10,000件、証拠本文2MB、保存本文合計32MBまでです。
注文・約定・建玉IDはSQLite整数の範囲、注文数量は10^12通貨までに制限します。
上限に達しても同じ内容の既計上約定は確認できますが、新規計上は拒否します。
自動削除・ローテーション・古いDBからの自動移行はありません。
全証拠を再検査するため、高頻度・長期運用の性能は残る課題です。

SQLiteのbusy（ロック競合）は破損と区別し、50ms間隔で最大3回（初回を含む）試します。
busyになったトランザクションはロールバックされているので、再試行で二重に計上することはありません。
3回とも競合した場合は `cash_book_busy` を返し、オブジェクトを使用不可にはしません。
読み取りは検証の間も共有ロックを保持します。2,000約定の台帳で約0.3秒（2026-10-02、ローカル計測）でした。
上限近くでは、別プロセスの診断と稼働中の計上が競合し得ます。

DBには口座情報と正規化した約定証拠が含まれます。認証キー・トークン・署名ヘッダーは保存しません。
暗号化は行わないため、他の口座記録と同じくストレージを保護し、Gitへ追加しないでください。

## 合成デモと検証

```powershell
uv run python -m trading.execution_cash_lab demo --directory runs/execution-cash-demo
uv run python -m trading.execution_cash_lab status --directory runs/execution-cash-demo
```

口座・認証情報・ネットワークを使わず、新規約定→重複→再起動後の重複→決済→残高一致→
説明できない100円差を再現します。未使用ディレクトリにDBと `report.json` を保存し、上書きしません。
例では開始100万円から、新規手数料2円と決済の受渡金額41円を反映して1,000,039円になります。

検証は `uv run pytest tests/test_execution_cash_book.py -q` です。
同時書込み、commit前後のプロセス終了、仕訳途中の失敗、重複、内容矛盾、欠損・書換え、
Decimal精度、境界、上限、時計許容差、残高差を合成入力で確認します。
実業者との疎通、電源断・ディスク障害の実機試験、初期履歴と入出金の実口座照合は未実施です。
