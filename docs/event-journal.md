# 変更通知の永続記録と履歴再生

2026-09-30。イベント保存専用のSQLiteと、保存後に診断モニターへ渡すアダプターを追加しました。
**WebSocket接続・キー読込・発注・自動再開はしません。** 口座なしの合成データで検証します。
既存のペーパーDB、注文台帳、GET制御DBとは別ディレクトリを使います。

## 保存と受渡しの順序

`JournaledEventCapture` は次の順に処理します。

1. 受信番号、時刻、対応する通知の形式を検査する。
2. `EVENT` と記録末尾のハッシュ・件数を同一トランザクションで確定する。
3. 既存の `AccountSyncMonitor` へ通知を渡す。
4. モニターへの受渡し完了を別の `ACK` 記録として確定する。

`ACK` は業者からの応答でも、取引成立・会計処理・完全同期の証拠でもありません。
タイムスタンプは対象入力の受信時刻を参照し、ACK処理の所要時間を測るものではありません。
保存前に失敗したら通知をモニターへ渡しません。
保存後・ACK前に停止した場合は `unacknowledged_records` に記録番号が残ります。
受渡しが実際には済んでいた可能性もあるため、「未処理」と断定せず**処理結果不明**として扱います。
通常の受渡し失敗は固定コードの `FAULT` も記録しますが、保存障害でそれすら記録できない場合もあります。

未確認記録がある同じ接続世代では後続入力を受け付けません。
再起動による自動ACK、自動再適用、自動削除はありません。
初期化済みDBの欠損・破損を検出しても、新規DBに置き換えません。

## 再起動・別プロセスとの関係

`EventJournal(...)` で既存記録を開いても、受信セッションは始まりません。
新しい `JournaledEventCapture` は未接続・再取得必要の状態です。
開始には `start_session(expected_head=...)` を明示的に呼びます。
`expected_head` は直前に確認した記録末尾で、その後別プロセスが追記していれば開始を拒否します。

開始に成功すると新しい接続世代になります。旧世代の追記・ACKをDBトランザクション内で拒否します。
これは旧プロセスの死亡確認やネットワーク切断ではなく、**この保存先への書込み資格の切替**です。
新世代を始める前に、運用側で旧受信処理・自動再起動を止める必要があります。
GET制御の未完了claimを解消する機能とは別です。

旧世代の処理結果不明記録は新世代でも保持します。
新しいREST観測が構造一致しても `journal_epoch_gap_not_repaired`、
該当記録があれば `journal_delivery_outcome_unknown` を診断結果に残します。
以前の「観測済み」状態やREST結果を、再起動後の使用可能な証拠として復元しません。
この版で永続保存するのは通知・死活確認・接続世代・受渡し結果で、REST収集結果そのものではありません。

## 整合性と情報保護

- DB識別子・scope・連続記録番号・前のハッシュ・本文を結びつけたSHA-256の連鎖を保存します。
  記録末尾・件数・本文バイト数も同じトランザクションで更新します。
- 開くとき、検査・再生・各追記の前に、件数・全連鎖・時刻・世代・受信番号・ACKの参照先を検査します。
  記録の欠損や不整合があれば拒否します。
- 書込みは `BEGIN IMMEDIATE` と `synchronous=FULL` を使います。
  状態検査・履歴再生はSQLiteの読み取り専用モードで行います。
- 保存対象の通知は既存パーサーが受理したものだけです。
  未対応・不正な通知は、固定理由コードと、サイズ内のbytes入力ならSHA-256だけを保存します。
  原文・例外本文・認証ヘッダー・アクセストークンは保存しません。
- 受理した通知には建玉・注文等の口座情報が含まれます。**DB自体は暗号化しません**。
  OSのアクセス権や暗号化されたストレージで保護し、Gitに追加しないでください。

ハッシュ連鎖は不整合の検出であり、署名や外部の改ざん防止装置ではありません。
DB全体と末尾情報を編集できる相手、整合した古いバックアップへの差し戻し、別DBによる迂回は防げません。
ローカルファイルと正常なSQLite・ストレージ動作が前提です。ネットワーク共有での利用は対象外です。

## 上限と未対応部分

既定で10,000記録（設定可能範囲4～20,000）、本文合計32MBまでです。
EVENTだけでなくBEGIN・ACK・HEARTBEAT等も件数に含めます。
上限に達したら拒否し、古い記録を自動削除したり、自動で別DBへ切り替えたりしません。
ACK直前に上限へ達する場合も、処理結果不明として残ります。
通知1件の入力上限は既存パーサーと同じ16KBです。

各操作で全記録を検査するため、長期間・高頻度の本番受信向けの性能調整やローテーションは未実装です。
受信アダプターへ届く前の欠落は証明できず、ローカル受信番号も業者側の連番ではありません。
通知記録の存在を、口座本人性・約定履歴の完全性・発注許可へ昇格させません。
すべての診断・履歴再生は `complete=false`、`live_enabled=false` です。

## 口座なしのデモ

```powershell
uv run python -m trading.event_journal_lab demo --directory runs/event-journal-demo --scope synthetic
uv run python -m trading.event_journal_lab status --directory runs/event-journal-demo --scope synthetic
uv run python -m trading.event_journal_lab replay --directory runs/event-journal-demo --scope synthetic
```

未使用ディレクトリに `event-journal.sqlite` と `report.json` を作ります。既存出力は上書きしません。
デモは正常な受渡し、ACKがない通知、新世代開始、新しい通知の受渡し、正常終了を模擬します。
終了しても旧世代の記録4が処理結果不明として残ります。

`replay` は確認済み入力を診断用に再生するだけで、生きたモニターを返しません。
処理結果不明の入力は再適用せず、履歴上の不確実性として表示します。
REST観測は保存していないので、履歴再生から「同期済み」を復元することはありません。
保存した過去の時計を使うため、同じ記録の再生結果は同じです。

検証:

```powershell
uv run pytest tests/test_event_journal.py tests/test_event_capture.py tests/test_event_journal_lab.py -q
```

別プロセスの強制終了、保存後・受渡し前の終了、旧世代の別プロセスからのACK拒否、
世代開始・追記の競合、保存失敗、欠損・書換え・意味上の不整合、期限・容量上限、
再取得中の通知、不正入力の本文非保存を検証します。
実業者API、実口座、電源断・ディスク障害の実機試験ではありません。

[既知注文のREST約定照合](execution-reconciliation.md)と
[WebSocket受信・トークン管理](private-stream.md)を追加しました。
実購読の受入確認、全口座会計・履歴の再同期、長期保存の運用が残っています。

## 2026-10-01 レビュー対応

`JournaledEventCapture(..., clock_skew_ms=100)` の許容幅はBEGIN記録に保存します。
検証・再オープン・履歴再生でも同じ値を使い、値のない旧記録は0msとして扱います。
既定は0ms、設定範囲は整数0〜1,000msです。新しい世代には前世代の設定を引き継ぎません。
許容幅を記録したジャーナルは、このフィールドを知らない旧版では検証を拒否します。

受渡し失敗後も読めるジャーナルを検査し、未ACK記録と
`journal_delivery_outcome_unknown` を `status()` に表示します。読めない場合だけ値をNoneにします。
通知ごとの重複した事前検査を除き、記録・ACKの各トランザクションで計2回検査します。
全履歴検証自体は維持するため、履歴の増加に伴う処理時間は残る制約です。
初期化失敗時は作成した既知ファイルを後始末し、再初期化可能にします。
既存ディレクトリや未知のファイルは削除しません。
