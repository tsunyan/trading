# 長期保存した履歴の再測定

2026-10-05。[測定スクリプト](../research/benchmark_retained_history.py)で、
通知ジャーナル約100MB・500MB・1GBと、運用通知1万・5万・10万件を、それぞれ3回測定しました。
[全18試行の生データ](../research/20261005-retained-history-benchmark.json)に成功・失敗の件数と
最小値・中央値・最大値を保存しています。今回の失敗は0件です。

各試行に別の一時DBを使い、生成したBEGIN・HEARTBEAT/ACK・ENDをすべて検証してから保存します。
監視の合成入力は送信済みと記録した通知と正常なREADY状態です。元の実口座・ペーパー口座・タスク・キーは使いません。
全体回帰が終了した後に測定しました。OSキャッシュの破棄や他プロセスの負荷制御はしていません。

## 通知ジャーナル

表は中央値（秒）です。本文量は十進MBで、SQLiteファイル全体の大きさとは異なります。

| 本文量・記録数 | 全解析監査 | 全保存バイト照合 | 再起動 | 照合と同時に開始した書込み |
| --- | ---: | ---: | ---: | ---: |
| 102.6MB・512,000件 | 5.247 | 0.102 | 0.101 | 0.117 |
| 513.0MB・2,560,000件 | 26.448 | 0.489 | 0.499 | 0.556 |
| 1,025.9MB・5,120,000件 | 53.537 | 0.986 | 1.001 | 1.102 |

最大サイズの全バイト照合の範囲は0.979〜1.007秒、同時書込みは1.101〜1.103秒でした。
同時書込みは各試行でcommitし、その後の現区間とセッションも検証しています。

## 運用通知の保存

表は中央値（秒）です。各DBの現行通知は1,000件で、残りは保存区間です。

| 総通知数・SQLite容量 | 状態確認 | 再起動 | 全監査 | check | 追記 | notify |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000件・5.6MB | 0.057 | 0.055 | 0.170 | 0.187 | 0.175 | 0.134 |
| 50,000件・29.5MB | 0.282 | 0.269 | 0.837 | 0.818 | 0.937 | 0.552 |
| 100,000件・59.6MB | 0.546 | 0.531 | 1.702 | 1.667 | 1.626 | 1.116 |

1万件のnotifyには最大1.002秒の試行もあり、中央値だけではばらつきを表せません。
実Windows通知は送らず、送信callbackは何もしない合成処理です。

## 判断と限界

[全保存バイトの照合を維持する方針](segmented-journal.md)を変える根拠は得られていません。
1GBで約1秒という結果は履歴量への比例を示しますが、実環境の時間保証ではありません。
この測定は暖まったWindows 11のローカル読取りで、ディスク・OS・SQLiteの競合、冷えた読取り、
実業者通信・WebSocket、全口座会計、監視と実発注の送信前経路全体を含みません。
各経路で何回検査されるかも、単独の照合時間から推測しません。

当面は完全性の検査を維持し、実機の保存量と送信前・監視経路全体を測定する工程を残します。
その結果が鮮度期限・監視間隔・SQLite待機時間に影響する場合に、検査頻度・保存階層・分割単位を
検討します。測定を理由に破損検知を外したり、口座や気配の鮮度期限を広げたりはしません。

再実行する場合は、新しい出力先を指定します。既存の測定結果は上書きしません。

```powershell
$env:OPENBLAS_NUM_THREADS='1'
uv run python research/benchmark_retained_history.py --output research/new-retained-history-benchmark.json
```

対象サイズ・試行数には生成量の上限があります。失敗した試行もartifactに記録し、終了コードを1にします。
集約した時間は成功した試行だけの値で、失敗がなかったと読み替えません。
