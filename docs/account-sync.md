# 口座変更通知とREST再取得の照合（オフライン基盤）

2026-09-30。`AccountSyncMonitor` と、記録を再生する `account_sync_lab` を追加しました。
**口座・APIキー不要。WebSocket接続、トークン発行、実注文、既存DB変更は行いません。**
ペーパー観測の固定コア・設定・スケジュールにも接続しません。

## 実装した範囲

- `positionEvents`、`orderEvents`、`executionEvents` の記録済みJSONを解析。
  現在の対応はUSD/JPY、注文系は顧客注文ID付きのNORMAL LIMIT、OPEN/CLOSEのみ。
  他銘柄・手動注文・未対応の型やフィールドを無視せず、その接続世代を無効化します。
- 建玉通知は数量・注文中数量・価格・売買方向・銘柄をREST建玉と比較。
  決済通知はRESTからの消失を確認します。
- 注文通知はID・親ID・顧客ID・銘柄・方向・区分・価格・総数量・状態を比較。
  取消・失効通知は有効注文一覧からの消失を確認します。
  全量約定通知（`orderExecutedSize == orderSize`）も、その注文IDの消失の根拠にします。
  部分約定では消失を許容せず、全量約定後も注文がRESTに残れば不一致です。
- 前の採用済み観測から建玉・注文の構造が変わったのに、対応する通知がなければ不一致。
  残高balanceの変化も別途確認が必要として拒否します。単に同じREST結果を再取得しても
  不一致を消しません。
- 約定通知は約定IDごとに保持し、同一IDの異なる内容は拒否します。
  同一通知の再配信でも再取得中の結果を無効にしますが、二重計上は行いません。
  [既知注文のREST約定との照合](execution-reconciliation.md)を任意の `collect_orders` で実行できます。
  約定の会計計上は未接続で、履歴完全性や会計反映の未検証条件を残します。
- ローカル受信番号の欠番・逆順、不正通知、切断、時計異常、保持上限到達で無効化します。
- 再取得は既存の `AccountReader.collect_account` を明示的に渡し、1回だけ実行します。
  取得中の通知・切断・再接続で結果を破棄し、古い接続の完了が新しい観測を上書きしないようにします。

数量は注文総量のまま比較し、未約定残量へ変換しません。
評価損益・累積スワップ・時刻の一致は構造照合に含めません。
このため `structural_match=true` は全会計項目の一致でも、原子的な同期完了でもありません。

## 公開仕様から分かる限界

[GMO FXのPrivate WebSocket仕様](https://api.coin.z.com/fxdocs/#private-ws-api)と、
[注文](https://api.coin.z.com/fxdocs/#ws-order-events)・
[約定](https://api.coin.z.com/fxdocs/#ws-execution-events)・
[建玉](https://api.coin.z.com/fxdocs/#ws-position-events)の通知項目を確認しました。

確認した通知フィールドにはストリーム全体の連続番号やRESTとの共通スナップショット境界がありません。
注文・建玉の時刻は注文日時や約定日時で、受信時刻や全イベントの順序としては使いません。
古い建玉の更新通知を、建玉の約定日時が古いという理由だけで拒否しない設計です。
なお、建玉通知の注文中数量キーは公開仕様どおり `orderdSize`、RESTは `orderedSize` です。

`receive_sequence` は**受信アダプターがデータフレームを取り込む際に付けるローカル番号**です。
最初は1、以後1ずつ増やします。約定IDを連番として扱ったり、業者がこの番号を配信すると仮定したりしません。
アダプターより前に落ちた通知、無通知の変化、受信順と業者処理順のずれを完全検出できません。
通知が来ないことも「変化なし」の証明ではありません。

## 状態と再取得手順

| 状態 | 意味 |
| --- | --- |
| `DISCONNECTED` | 未接続、切断、欠番、不正入力、死活確認期限切れ等。旧世代は再使用不可 |
| `NEEDS_RESYNC` | 接続世代開始直後、変更通知あり、照合不一致、観測期限切れ |
| `COLLECTING` | 全口座を再取得中。新しい変更が届けば結果を採用しない |
| `OBSERVED_UNVERIFIED` | 観測した構造の矛盾が見つからなかっただけ。完全性・発注許可は未確認 |

1. `start_session()` で新しいローカル接続世代を作る。ネットワークは開かない。
2. 受信したデータフレームを `ingest(session, receive_sequence, payload_bytes)` へ渡す。
3. 実際に受信したping/pong等を `heartbeat(session)` へ伝える。
4. `resync(session, reader.collect_account)` を明示実行する。不一致なら原因を調べ、必要に応じて全再取得する。
5. 切断後は新しい接続世代と新しい観測を作る。これは欠損履歴の復元ではない。

再取得コールバックの間はモニターのロックを保持せず、通知処理を止めません。
採用時に接続世代・変更リビジョン・時刻を再検査します。
ローカル受信時刻が開始前のREST結果は拒否します。業者応答時刻には
`AccountSyncMonitor(..., clock_skew_ms=100)` のように時計差の許容幅を指定できます。
整数0〜1,000ms、既定0msで、開始より前／受信より未来の業者時刻にだけ適用します。
通知の未来時刻にも同じ許容幅を適用します。範囲外の通知は接続世代を終了し、
ジャーナル利用時はREJECTEDになります。ReaderとCapture/Monitorには実測に基づく同じ値を
明示設定してください。100msは例示で、実口座での校正値ではありません。
時計の逆行・受信順・取得期限は従来どおり検査します。

デフォルトのローカル安全側設定は、死活確認75秒・再取得上限30秒・採用した観測の有効期間30秒・
接続世代あたり最大1,000データフレームです。死活確認は公開仕様の1分間隔pingを踏まえた設定で、
業者が保証する配送期限ではありません。他の数値も実口座で調整済みの運用値ではありません。
heartbeatだけでは観測の有効期間を延長しません。
このクラスはタイマーやバックグラウンド処理を起動せず、期限検査は各メソッド・`status()` 呼出時です。

## 発注への接続はしない

診断結果は常に `complete=false`、`live_enabled=false` です。
REST側の本人性・原子性・履歴完全性・費用計算の未確認条件に加え、イベントの連続性と
資産変化の網羅性の未確認条件を残します。再接続後も `history_gap_not_repaired` を残します。
未照合の約定通知があれば `execution_events_not_reconciled` と該当約定IDを表示します。
任意のREST約定照合も指定した場合、`structural_match` はその不一致も含めた判定になります。
すべての比較が一致した観測でのみ照合済み表示を採用し、会計反映の未確認条件は維持します。

`resync_required=false` は、現在の構造観測について再取得要求が解消したという意味だけです。
残高の正しさ・履歴完全性や発注可否を示しません。
既存の `AccountSnapshot`、注文台帳、GET停止解除への変換経路はありません。
モニター自体はプロセス内・非永続の診断用で、再起動時は未接続からやり直します。
別途[通知の永続記録アダプター](event-journal.md)を追加しました。
通知を保存してからモニターへ渡し、未確認の受渡しや接続世代の境界を保持しますが、
以前の観測済み状態やREST結果を使用可能な証拠として復元しません。

## 口座なしのデモ・再生

```powershell
uv run python -m trading.account_sync_lab demo --directory runs/account-sync-demo
uv run python -m trading.account_sync_lab replay --input runs/account-sync-demo/transcript.json
```

未使用ディレクトリを指定します。既存出力は上書きしません。
`transcript.json` と `report.json` を出力します。デモは次の9段階です。

接続世代作成 → 400通貨を観測 → 600通貨への変更通知 → 古い400通貨のRESTを拒否 →
600通貨のRESTと構造一致 → ローカル受信番号の欠番で切断扱い → 新世代 → 新観測 → 死活期限切れ。

再生は記録時刻を使い、同じ記録なら同じ結果になります。実ネットワーク・実時計の待機はありません。
ファイル入力は2MB、最大2,000ステップ、イベントフレームは16KBまで。重複JSONキーも拒否します。
将来実口座の記録を扱う場合、結果と入力は口座情報として保護し、認証情報を含めたりGitへ追加したりしないでください。
