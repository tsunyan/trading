# 自動送信の設計案（未実装・要判断）

2026-10-04作成。現在の実発注は、送信ごとに運用者が実行内容のSHA-256を確認して`order_runtime submit`を
実行する設計です。毎時の足で動く戦略を無人で運用するには、提案をそのまま送信する仕組みが必要になります。
実資金を人の確認なしに動かすため、実装するかどうかは運用者が判断してください。この文書は判断材料です。

## 現状で既にある安全装置

- 期限付きの有効化（最大7日）と、受入証拠・確認項目つきの承認
- 送信直前の口座リスク検査（注文額・総建玉額・レバレッジ・維持率・余力・損失上限・ドローダウン）
- 損失による新規停止（決済は継続）、独立監視からの停止、同期・監視の送信前検査
- POST制御による1件ずつの送信、結果不明時の停止と再送しない設計
- 実運用に昇格した戦略候補だけに新規を限る昇格管理（指定時）

## 自動送信に追加で必要と考えるもの

1. **常設の自動送信許可**: 有効化とは別の、期限付き（例: 24時間）の許可を承認ファイルで与える。
   許可には戦略候補（台帳の仮説と設定SHA-256）、1回の最大数量、1日の最大送信回数、1日の最大損失を固定する。
2. **送信の条件**: 許可の範囲内、同期・監視が健全、提案が戦略の新規・決済（手仕舞いは常に可）、
   直前のサイクルで口座証拠を更新済み、気配が鮮度内。どれかを外れたら送信せず通知する。
3. **1回のサイクルで1件**: 送信後は受付・照合が終わるまで次を送らない（現状の未決済注文の見送りと同じ）。
4. **通知**: 送信ごとに通知し、日次で送信件数・損益を通知する。
5. **緊急停止**: `live_setup stop`と`post_control stop`のほか、許可ファイルの取り消し（失効）で即座に止まる。
6. **結果不明時**: 現状どおり停止し、自動では再送・解消しない。

## 実装の見積もり

- 自動送信許可のモデルと保存（台帳とは別のファイル、またはPOST制御の記録）: 中
- `live_cycle --auto-send`: 準備→実行内容→発注用キーの読込→送信を1回で行う。既存の確認済み送信の
  検査をすべて通す: 中
- 日次の回数・損失の上限の集計と検査: 小〜中
- 試験（許可の範囲外・期限切れ・回数超過・損失超過・同期不健全・結果不明での停止）: 中

## 判断してほしい点

- 自動送信を実装するか。するなら、最初は実口座の受入試行を手動送信で終えてからにするか。
- 許可の既定の期限（例: 24時間）、1日の最大送信回数、1日の最大損失。
- 自動送信中の新規を、昇格管理で`live`になった候補だけに必須とするか（推奨: 必須）。
