# 決済注文による建玉拘束の照合

2026-10-02。宣言した開始建玉と計上済み約定を使い、決済注文が拘束する数量を
REST建玉の `ordered_units` と比較する `ExecutionCashBook.compare_reservations` を追加しました。
比較は非永続の診断です。注文送信・取消、残高・建玉の補正、発注許可は行いません。

## 元の注文意図と個別証拠

開始建玉を明示したversion 2／3の台帳で使います。version 1では建玉なしと推測せず拒否します。
注文の元の `OrderIntent`、既知注文ID、`AccountReader.collect_order` の結果を呼出側で用意します。
RESTの未約定注文には建玉ごとの決済割当が含まれないため、そこから元の割当を推定しません。

```python
# known_orders は、元の注文意図と既知の注文IDの組合せ。
# active注文だけでなく、取消・失効・全約定を確認したい注文も含められます。
order_reports = tuple(reader.collect_order(intent, order_id) for intent, order_id in known_orders)
account = reader.collect_account()
comparison = book.compare_reservations(account, order_reports)
```

すべてのREST未約定注文に対応する個別資料を要求します。資料がない注文は
`reservation_order_not_collected` とし、未確認の注文IDを返します。
注文意図と実口座本人性の対応は未認証で、渡された資料が全注文を網羅することも未証明です。
現在の注文台帳から意図を自動で取り込む処理や、同期モニターからの自動実行はありません。

## 残数量の計算

照合対象は `ORDERED` の通常指値注文です。買い建玉は売り決済、売り建玉は買い決済を要求します。
`WAITING`・`MODIFYING` は拘束状態を確定できないため、期待数量を返しません。
これは明示した意図からのローカル計算で、業者の拘束規則は未検証です。

決済注文ごとに、元の建玉別割当から、その注文の計上済み決済約定を建玉別に引きます。
複数注文が同じ建玉を使う場合は残数量を合算します。未約定注文の `units` は注文総数量なので、
そのまま残数量や拘束数量として使いません。新規注文は既存建玉を拘束しません。

| 状態 | 保有数量 | 注文総数量 | 計上済み決済 | 期待拘束数量 | 非拘束数量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 決済注文中 | 400 | 300 | 0 | 300 | 100 |
| 100通貨を部分決済 | 300 | 300 | 100 | 200 | 100 |
| 残数量の取消を確認 | 300 | 300 | 100 | 0 | 300 |

REST個別約定は、ID・注文意図・親注文ID・金額を含む内容が台帳と一致し、すべて計上済みである必要が
あります。未計上約定、既計上約定の消失、内容変更、別注文へのIDや顧客注文IDの再利用は差異です。
比較APIが不足約定を自動計上することはありません。開始境界以前の約定を含む資料も、
台帳にない約定を開始建玉へ吸収せず未確認として返します。

`CANCELED`・`EXPIRED`・`EXECUTED` の個別資料があり、REST未約定注文から消えている場合は、
残った割当を拘束数量へ加算しません。取消前の部分約定は台帳に残ります。
全約定資料は注文総数量分の約定を要求します。残数量0の注文が未約定一覧に残る場合も差異です。
これらの資料だけで注文が再び有効にならないことまで証明するものではありません。

## 比較結果と不確実性

`reservation_match` は今回の資料と台帳に対する比較だけです。`mismatches`、
`unverified_order_ids`、注文別の残数量、建玉別の期待拘束数量・REST拘束数量・非拘束数量を返します。
未確認注文があれば、割当先も不明になり得るため、全建玉の期待数量と非拘束数量を `None` にします。
確認済み注文の内訳は診断用に残りますが、全体の拘束数量として使えません。

保有建玉のID・方向・数量も比較します。割当先不明、方向矛盾、保有数量を超える拘束、
RESTとの数量差を補正しません。取得価格・含み損益・証拠金は、この拘束比較の対象外です。
取得価格の検証は [compare_positions](execution-positions.md) で行います。
複数の比較結果を一緒に使う場合は、返された `head` が同じ台帳状態を指すことを確認してください。

結果には、読み取った台帳の末尾ハッシュと停止状態を含みます。
version 3では約定と入出金の両方を含む `head` を使います。比較中の後続書込みにより、
結果が現在の台帳と一致するとは限りません。照合自体はDBの同じ読取りトランザクションで行います。
比較による差異は永続停止を新たに記録せず、既存の永続停止も解除しません。

## 入力検査と時刻

個別資料は0〜1,000件のtuple、個別約定の合計は10,000件まで、
口座レポートと個別資料の正規化本文合計は2MBまでです。建玉と未約定注文は各1,000件までです。
IDはSQLite整数の範囲、数量は10^12通貨まで、金額は既存台帳と同じ固定精度・範囲で検査します。
呼出側が検証を省略して作ったモデルも再検証します。

個別資料の要求パス・注文ID・4回の観測順・SHA-256形式・約定内容を検査します。
`executions_complete=true` の自己申告は受け付けません。繰り返し一致した資料を使っても、
失った履歴や原子的な状態の証明にはなりません。

個別注文の資料を先に集め、その後に口座レポートを集めます。
全個別資料の応答・受信時刻が口座観測の開始より後になる入力を拒否します。
個別資料と口座資料が台帳の開始境界や最新の計上済み約定より古い場合も拒否します。
口座資料は最新の計上済み入出金以降を要求します。
`clock_skew_ms` は既存Readerと同じ実測値を指定し、整数0〜1,000ms、既定0です。
異なる収集時点の変化や現在時刻に対する鮮度は、この非永続APIだけでは保証しません。

一致しても `complete=false`、`live_enabled=false` です。原子的な口座観測、
開始残高・開始建玉・全履歴、注文意図の認証、業者の拘束規則、実口座受入検証が残ります。
