- レビュー日: 2026-09-28
- 対象: ブランチ `feat/fetch-resume-lineage`（`main` の `5d1fcb1` からの未コミット変更）
- 変更ファイル: `src/trading/cli.py`、`data.py`、`evaluation.py`、`gmo.py`、`tests/test_data.py`、`test_evaluation.py`、`test_gmo.py`、`README.md`、`docs/roadmap.md`
- 確認したこと: `uv run pytest`（124件合格）、`uv run ruff check`、`uv run ruff format --check`（いずれも問題なし）

## 結論

大きな問題はなく、方向性は妥当です。特に次の点はよくできています。

- チェックポイントを再開するときは、保存したリクエスト（銘柄・足の長さ・期間）と照合します。別のリクエストのチェックポイントは使わずに拒否します。
- 取引日ごとの保存ファイルも、中身が本当にその取引日の足かを読み直して確認します。
- ファイルは一時ファイルに書き切ってから `os.link` で公開します。そのため、書きかけのファイルが見えることはなく、既存ファイルを置き換えることもありません。
- 系譜ファイル（`<出力名>.lineage.json`）にデータの SHA-256 を記録し、読み込み時に照合します。`merge-bars` は入力の系譜ハッシュもつなげて記録するため、結合結果から元の取得ファイルまでたどれます。

一方で、**空白を誤って「正常」と判定してしまう経路が1つあります**（下の指摘1）。空白分類の信頼性に直結するため、マージ前の修正を勧めます。

README で出典にしている [GMOコインの取引時間ページ](https://coin.z.com/jp/corp/product/info/fx/) も確認しました。「月曜日7:00〜土曜日5:59」は夏時間・冬時間の区別なく通年の表記で、`_regular_fx_closure` の定義と一致しています。

## 指摘（修正を勧めるもの）

### 1. まだ確定足がない日が「APIが空を返した日」として記録される

- 場所: `src/trading/gmo.py:159`（未確定の足を除く処理）→ `src/trading/cli.py:120`（`.empty` の作成）→ `src/trading/cli.py:323`（`merge-bars` での空の日の和集合）
- 内容: `candle_days` は、未確定の足を除いた結果が空になった日も、空の日として返します。`_fetch_fx` はそれを API が正常に空を返した日と区別せず、`.empty` を作って系譜の `empty_trading_dates` に載せます。
- 起きる例:
  1. 平日の JST 6:00〜8:00 に、`--end` を当日にして `fetch-fx` を実行します。まだ確定足が1本もないため、当日が空の日として記録されます。
  2. 後で当日分を含めて別に取得し、`merge-bars` で結合します。
  3. `merge-bars` は入力の空の日の和集合を取るので、足がある日なのに空の日として残ります。
  4. その日に本当の欠損があっても `provider_empty` に分類され、`status: ok` になります。
- 対策案:
  - 未確定の足を除いたために空になった場合は、空の日として扱わない（`.empty` を作らない、または当日を空の日の扱いから外す）。
  - `merge-bars` または `interval_gap_report` で、足が存在する日を空の日から除くか、矛盾として拒否する。

### 2. データ本体を公開した後に系譜を書くため、途中で失敗すると復旧できない

- 場所: `src/trading/cli.py:135` → `src/trading/cli.py:148`（`fetch-fx`）、`src/trading/cli.py:351` 付近（`merge-bars`）
- 内容: 出力を先に `os.link` で公開し、その後で `interval_gap_report`、`source_sha256()`、`runtime_versions()`、`write_data_lineage` を実行しています。
- 起きること: この間で失敗すると、系譜のない出力が残ります。再実行しても「出力が既にある」で拒否されます。`fetch-fx` ではチェックポイントも残ったままになり、手作業でファイルを削除するしかありません。
- 対策案: 系譜の記録内容を出力の公開前に組み立てておき、公開後に失敗しうる処理を `write_data_lineage` の書き込みだけに絞ります。

## 軽微な点・設計上の注意

### 3. ハードリンクに対応しない保存先では動かない

- 場所: `src/trading/cli.py:48`、`src/trading/data.py:89`
- exFAT、一部の SMB 共有、クラウド同期フォルダなどはハードリンクに対応していません。以前の `write_bars` はこうした場所でも動いていたため、互換性の後退になります。
- README に制約を書くか、失敗時のエラーメッセージで原因が分かるようにすると親切です。

### 4. API 側の障害でも `status: ok` になりうる

- API が平日に障害で空配列を返した場合も `provider_empty` になり、要確認に上がりません。
- README に書いた方針どおりの挙動ですが、ロードマップの「取得障害による空白の分類」を完全には満たしていません。
- 選択肢: 通常の取引時間内（平日）の `provider_empty` だけは `needs_review` に残す。

### 5. 同じファイルを何度もハッシュ計算している

- `merge-bars` では、入力1つにつき SHA-256 を3回計算します（`read_bars` 内の `read_data_lineage`、`describe_data_artifact` 内の `read_data_lineage`、`describe_data_artifact` 内の `file_sha256`）。
- 大きなファイルではその分遅くなります。ハッシュを一度だけ計算して使い回せば十分です。

### 6. `interval_gap_report` が全行を Python で回している

- 場所: `src/trading/evaluation.py:45`
- `diff()` で空白だけを先に抜き出し、その空白にだけループを回せば十分です。`compare` で何度も呼ぶ場合に効いてきます。

### 7. 系譜に絶対パスが入る

- 場所: `src/trading/data.py:48`（`describe_data_artifact`）、`write_data_lineage` の `artifact.path`
- `resolve()` した絶対パスを記録するため、別のマシンでは一致しません。照合はハッシュで行っているので実害はありませんが、ローカルのパスが成果物に残ります。

### 8. テストの抜け

- 指摘1のケース（未確定の足を除いて空になった日と、その後の `merge-bars`）のテストがありません。
- 指摘2のケース（出力の公開後に系譜の書き込みが失敗する）のテストがありません。

## 修正後の再確認（2026-09-28）

- 確認したこと: `uv run pytest`（130件合格）、`uv run ruff check`、`uv run ruff format --check`（いずれも問題なし）

| 指摘 | 結果 | 修正内容 |
|---|---|---|
| 1. 未確定の足による空の日 | 解消 | `candle_days` が空の理由（`provider_empty` / `current_trading_date` / `incomplete_only`）と取引日が終わったかどうかを返し、`fetch-fx` は終わった取引日の空応答だけを `.empty` として記録する。進行中の取引日はチェックポイントに保存せず停止する。`merge-bars` は足がある日を空の日から除いて `superseded_empty_trading_dates` に記録し、`interval_gap_report` も矛盾を `lineage_empty_date_conflicts` として要確認にする |
| 2. 公開後の系譜書き込み失敗 | 解消 | 系譜の記録内容と一時ファイルを公開前にすべて用意し、`_publish_data_artifact` がデータと系譜の両方を公開する。系譜の公開に失敗したらデータも取り消す |
| 3. ハードリンク非対応の保存先 | 解消 | `publish_new_file` が原因を含むエラーを出し、README にも制約を追記 |
| 4. API 障害でも `status: ok` | 解消 | `provider_empty` も `needs_review` にし、理由を `review_reasons` に出す。ロードマップも「一部」に戻し、残りを明記 |
| 5. ハッシュの重複計算 | 解消 | `read_bars` が一度だけ計算し、`attrs["artifact"]` を `merge-bars` で使い回す |
| 6. 全行ループ | 解消 | `diff()` で空白だけを抜き出してからループする |
| 7. 絶対パス | 解消 | 系譜にはファイル名だけを記録する |
| 8. テストの抜け | 解消 | 未確定の足だけの日、進行中の取引日、系譜の公開失敗時の取り消し、ハードリンクのエラー、空の日と足の矛盾、`incomplete_only` の区別のテストを追加 |

### 残っている軽微な点（マージを止めるものではない）

- **当日を `--end` にした場合は最後の日まで取得してから止まる。** 前日までの分はチェックポイントに残りますが、同じ引数で再開できるのは翌日の 06:00 JST 以降です。`--end` を変えると「別のリクエスト」として拒否されるため、すぐ続けたい場合はチェックポイントを手で消す必要があります。`_fetch_fx` の冒頭で `end >= trading_date(now)` を拒否すれば、チェックポイントを作る前に止められます。
- **準備段階で失敗すると一時ファイルが残る。** `_publish_data_artifact` では、`write_bars` と `prepare_data_lineage` が `try` の外にあります。ここで失敗すると、データの一時ファイル（`.<名前>.<uuid>.tmp...`）が消されずに残ります。どちらも `try` の中に入れれば解消します。
  - PR #9 のレビュー指摘を受けて解消済み。`_publish_data_artifact` と `_commit_new_file` の両方で準備処理を `try` の中に移し、テスト（`test_merge_removes_staged_data_when_lineage_preparation_fails`）を追加した。
