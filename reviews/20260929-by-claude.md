## 結論

バックテストの BID/ASK 約定モデルは筋がよく、固定スプレッドの従来モードとも一致しています。

- 固定モードの `buy_open` / `sell_close` は、従来の「中値 ± スプレッド/2 ± スリッページ」と同じ値になります。そのため、既存の結果は変わりません。
- BID/ASK モードでは、中値が BID/ASK の中点と一致することを `validate_bars` で保証しています。`risk_bid_low` は実質的に `bid_low` になり、証拠金判定の逆行値として妥当です。
- `BidAskBroker` はチート・オン・オープン/クローズを拒否し、次の足の始値で約定します。

一方で、**オフライン注文台帳（`order_journal.py`）には、正常な運用手順の途中で台帳が永続停止する経路があります**（下の指摘1・3）。停止を解除するコマンドはないため、実運用に近づける前に直すことを勧めます。

## 指摘（修正を勧めるもの）

### 1. 注文の処理中に口座を更新すると、台帳が永続停止する

- 場所: `src/trading/order_journal.py:149`〜`165`、`src/trading/account_guard.py:120`
- 内容: `update_account` は、`reconcile_account` が返したエラーをすべて永続停止（`metadata.halted=1`）として扱います。その中には、口座の不整合ではなく「待てば解消する」状態も含まれます。
  - 注文が `SUBMITTING` / `UNKNOWN` / `CANCEL_PENDING` / `RECONCILING` のとき、`expected_account` が `unresolved_order` を送出する
  - 気配や口座スナップショットが古い、または未来時刻（`stale_or_future_quote` / `stale_or_future_account`）
- 起きる例:
  1. 注文が `WORKING` の状態で `begin_cancel` を呼ぶ（状態は `CANCEL_PENDING`）。
  2. ブローカーが取消を確定する前に、口座スナップショットを更新する。
  3. `unresolved_order` になり、台帳が永続停止する。以後、新規注文は一切できない。
  - 収集処理が少し遅れて気配が61秒前のものになった場合も、同じく永続停止します。
- `docs/account-guard.md` では、永続停止は「外部注文・外部建玉、説明不能な残高差異」のためのものとされています。時刻や手順のずれは、`evaluate_risk` が時刻不正を扱うのと同じように、停止せず `OrderBlocked` で拒否するだけにするのが妥当です。

### 2. 取消が拒否されると、`CANCEL_PENDING` から抜けられない

- 場所: `src/trading/order_journal.py:402`、`416`、`375`
- 内容: `cancellation_response` が `accepted=False` を返しても、状態は `CANCEL_PENDING` のままです。
  - `begin_cancel` は `WORKING` / `PARTIAL` しか受け付けないため、取消を再送できません。
  - `_reconcile` は、ブローカーがまだ注文中と返しても `CANCEL_PENDING` を維持します。
- 起きること: 取消が一時的に拒否された（`failed` 側に入った）だけで、その注文が約定か失効するまで、ほかの注文はすべて `_available` で止まります。無期限の指値なら、いつまでも止まったままです。
- 対策案: 受付されなかった応答では `WORKING` / `PARTIAL` に戻す。または、`CANCEL_PENDING` からの `begin_cancel` を許す。

### 3. 約定済みの注文を照合し直すと、証拠が上書きされ口座の照合が無効になる

- 場所: `src/trading/order_journal.py:377`〜`387`
- 内容: 終了済み（`FILLED` など）の注文に、約定内容が同じで `observed_at` だけ新しい証拠を渡すと、終了済みのチェックを通り抜けて `evidence_json` が上書きされます。
- 起きる例:
  1. 注文が `FILLED` で、口座の照合も有効な状態。
  2. 監視ループが `/orders` と `/executions` を取り直し、同じ約定を新しい `observed_at` で `reconcile` する。
  3. `revision()` が変わるため、口座の照合が無効になり、`begin_submission` が止まる。
  4. 次の `update_account` のスナップショットが、手順2より前に取得されたものだと `account_precedes_order_evidence` になり、永続停止する（指摘1と重なる）。
- 対策案: 終了済みの注文で、`observed_at` 以外の証拠が変わっていなければ何もしない。

### 4. ダッシュボードの起動確認が、503 やタイムアウトを「未起動」と誤認する

- 場所: `src/trading/paper_dashboard.py:203`
- 内容: `running()` は `URLError` をすべて「起動していない」と扱います。`HTTPError`（503 を含む）も `URLError` の一種です。
- 起きる例:
  - 起動中のダッシュボードが、`paper.sqlite` の書き込み中などで 503（Observation data unavailable）を返すと、同じポートで2つ目のサーバーを起動しようとして失敗します。その結果「port may be occupied」という誤解を招くエラーになります。
  - 応答が2秒を超えると、読み込みタイムアウトの `TimeoutError` が捕捉されず、そのまま落ちます。

### 5. ダッシュボードの約定表が買い持ちだけを前提にしている

- 場所: `src/trading/dashboard.html:50`
- 内容: 数量がマイナスの約定はすべて「決済」、プラスはすべて「買い」と表示されます。`paper.py` は `allow_short=true` なら `sell_short` を出します。
- 起きること: 売り持ちの新規が「決済」、買い戻しが「買い」と表示されます。スナップショットの約定には `action` が入っているので、それを使って表示するのが確実です。

## 軽微な点・設計上の注意

### 6. 買い持ちベンチマークで、足の検証が BID/ASK モードだけになっている

- 場所: `src/trading/evaluation.py:140`
- `buy_and_hold_benchmark` は、BID/ASK モードのときだけ `validate_bars` を呼びます。固定モードでは未検証のフレームに対して `execution_prices` を計算し、ラベルを位置として `iloc` で使います。
- 並び順やインデックスが崩れたフレームを渡すと、エントリーの足がずれるか、分かりにくいエラーになります。モードに関係なく検証すれば、分岐もなくなります。

### 7. 固定モードでも観測スプレッド倍率を受け付け、記録してしまう

- 場所: `src/trading/execution.py:17`、`19`
- 固定モードでは `observed_spread_multiplier` を使いませんが、値は受け付けられ、`stressed()` で掛け算もされます。そのため、効いていない倍率がレポートや台帳に記録されます。
- 固定モードで1以外を指定したら拒否するバリデーターを入れると、監査時の誤解を防げます。

### 8. 固定モードの約定価格の計算が2か所にある

- 場所: `src/trading/backtest.py:335`、`367`
- BID/ASK モードでは事前計算した価格で約定しますが、固定モードは Backtrader の `set_slippage_fixed` で約定します。一方で、ベンチマーク・発注数量の見積もり・清算価値は `execution_prices` の値を使います。
- 現在は両者が一致していますが、片方だけ変更すると食い違います。両モードで `BidAskBroker` を使えば、スリッページ設定と `kwargs = {"price": ...}` の分岐も不要になります。

### 9. 終了状態の集合が2か所で定義されている

- 場所: `src/trading/account_guard.py:18`（`DONE`）、`src/trading/order_journal.py:29`（`TERMINAL`）
- 中身は同じです。片方にだけ状態（たとえば `REJECTED`）を追加すると、台帳は注文を終了扱いにする一方、`expected_account` は `unresolved_order` を出すことになります。現状では、それが指摘1の永続停止につながります。1か所で定義して import することを勧めます。

### 10. 新規注文の評価損バッファの式が重複している

- 場所: `src/trading/account_guard.py:284`〜`291`、`298`〜`304`
- 「買いなら 基準価格−BID、売りなら ASK−基準価格（0未満は0）」の計算が、未約定の注文と今回の注文とで別々に書かれています。片方だけ直すと、リスク判定が食い違います。小さな関数に切り出すのが安全です。

### 気づいた点（修正は不要）

- 取消の応答自体がエラー（`status≠0`）だった場合は、`CANCEL_PENDING` のまま残ります。`unknown()` で状態不明にしてから照合し直せば取消できる状態に戻れるので、行き詰まりはしません。
- 固定モードでも、発注時の資金チェックは中値ではなく見積もり価格（`buy_close` / `sell_close`）で行うようになりました。発注数量の計算と同じ価格なので、一貫性は上がっています。上の比較では、結果への影響はありませんでした。
- ダッシュボードの見出しの「買いのみ」は固定文字列です。`allow_short=true` の口座で観測するなら、設定値から表示するよう直す必要があります。
