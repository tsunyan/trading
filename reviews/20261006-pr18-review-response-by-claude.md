# PR #18 のレビューへの対応

対象: [20261006-pr18-review-by-chatgpt.md](20261006-pr18-review-by-chatgpt.md)（レビュー時のhead `bc845f1`）と、
同じ範囲のCodeRabbitのレビュー
対応: 2026-10-06、`test/trim-slow-suite`の`c037e54`と`73a6aef`

ChatGPTのC1〜C5と、CodeRabbitの5件（E1〜E5）を現在のコードで確認し、すべて修正しました。
削ったケースは、ChatGPTの基準で1回目の削減全体を見直しました。基準は「値の組み合わせは減らしてよいが、
独立した状態フィールド・安全条件・永続化の境界には、それぞれ直接のケースを1つ以上残す」です。
指摘された箇所のほかにも、この基準に当たるケースを戻しています。

対応後の全体テストは、手元の既定設定（8プロセス）で2,729件と65 subtestsが合格し、47.6秒でした。
戻したのは53件で、全体の時間はほとんど変わっていません。Ruffの検査と整形確認も合格しています。

## 補足

- E1・E5と同じ形の固定時間の依存が、`test_private_supervisor.py`の終了テストにもありました。50ms後に収集を
  終わらせていたものを、`close()`が待ち始めた時点で終わらせる形にしました（`c037e54`）。
- `clock_invalid`は値違いではありませんでした。post controlは、この停止を`operator_stop`とともに上書きできない
  停止として別に扱っています。
- 次の削減は残しています。ChatGPTのレビューで「妥当」とされた範囲です。
  - 1つの容量チェックが全部を受け持つ、保存先と段階の全組み合わせ
  - 2×2の組み合わせのうち対角だけ（各次元のどの値も1回は通る）
  - 汎用の非200経路を通るHTTPステータス（429とリダイレクトの302は残した）
  - 同じフィールドの値違い（注文の状態、記録の上限、クライアント終了前の状態、空の参照）と、長い注文ループの回数
  - 単純なholdのサイクル（評価額のずれのケースが、最後に同じholdの経路を通る）
  - 上位互換のテストがある重複（doctorの容量テスト2件と、実時間2秒のタイムアウト）
- 戻した各ケースの子プロセスのコードは、もとの分岐をそのまま使っています。到達しない分岐が残っていないことは、
  パラメータの値と`if`の条件を突き合わせるスクリプトで確かめました。
