## 結論

このリポジトリは**「正しく損益を測る」ための道具は丁寧に作られていますが、「稼ぐ」ための部品はほぼ未着手**です。
具体的には次の4つが欠けています。

1. **稼げる規模の設計がない。** 現設定で仮に優れた戦略が見つかっても、期待利益は年に数万円の水準です（下の試算を参照）。
2. **エッジの有無を判定する基準が弱い。** `evaluate` の `candidate` 判定は「プラスで終わった」ことしか見ておらず、ベンチマーク（持ち続けるだけ）にも統計的偶然にも勝つことを求めていません。
3. **検証に必要なデータを作れない。** 評価ゲートは180日以上を要求しますが、手元データは12日分で、長期データを積み上げるコマンドがありません。
4. **稼働していない。** 模擬売買は手動実行のみで、2026-09-22 の約15時間分（61イベント、買い1回）で止まっています。

ソフトウェアの品質面は良好で、既存レビューの評価に同意します。問題は品質ではなく、**収益に直結する部分がまだ手付かず**という点です。

## 1. 数字で見る現状: 今の設定でいくら稼げるか

`configs/fx.toml` と `runs/paper.sqlite` の実際の状態から試算しました。

| 項目 | 値 | 出典 |
| --- | --- | --- |
| 仮想元本 | 1,000,000 円 | `initial_cash` |
| 1回の建玉 | 1,267 USD（約20万円） | paper DB の `units` |
| 遊んでいる現金 | 約80万円（金利ゼロとして扱われる） | `allocation = 0.20` |
| USD/JPY が1円動いたときの損益 | 約1,267 円 | 1,267 × 1円 |
| 往復の取引コスト（設定上） | 約26 円 | スプレッド0.01＋滑り0.002×2、手数料0.002%×2 |
| 1時間足の値幅（中央値） | 約0.23 円 | `data/usdjpy_hourly.parquet` |

**期待利益の上限感:** USD/JPY の年間変動率を約10%とすると、建玉20万円の損益のばらつきは年約2万円（元本の約2%）です。
シャープレシオ1.0（個人の戦略としてはかなり良い部類）でも**期待利益は年約2万円、税引後（20.315%）で約1.6万円**です。

**導かれること**

- 今の制約（レバレッジなし・20%配分・買いのみ・1銘柄）のままでは、どんな戦略でも「稼ぐ」水準には届きません。
  これは戦略の良し悪しではなく**設計上の上限**です。
- コストは1時間足の値幅に比べて十分小さく、**課題は「コスト」ではなく「エッジ」と「資金効率」**です。
- 最大ドローダウン停止（5%）は**実質的に機能していません**。建玉20万円で元本の5%（5万円）を失うには、USD/JPY が約39円（約25%）下落する必要があります。
  バックテストの `drawdown_within_limit` 判定も、同じ理由でほぼ必ず通ります（`evaluation.py:121`）。

### 必要なもの

- **目標の数値化**: 「年率○%・最大DD○%・元本○円・投入できる時間」を決め、そこから必要なシャープレシオ、レバレッジ、取引頻度を逆算する文書。これがないと、研究をいつ止めるか・いつ実弾に進むかを判断できません。
- **ポジションサイジングの抽象化**: 固定比率ではなく、ボラティリティ目標（例: 年率10%）による建玉決定。レバレッジを使う場合は、証拠金とロスカットのモデルが前提になります。
- **リスク上限を建玉基準で定義する**: 口座全体のDDだけでなく、1トレード当たりの許容損失（ストップ）と、ボラティリティで調整した建玉上限。
- **現金の機会費用**: 遊休資金の金利（円預金、または無リスク金利）を評価に入れ、「何もしない」と比較できるようにする。

## 2. エッジ判定: `candidate` が甘い

`evaluation.py` は時系列分割とコスト2倍のストレス検証を入れていて方向性は正しいです。ただし、**稼げるかどうかの判定**としては以下が不足しています。

### 2.1 ベンチマークとの比較がない（最重要）

`performance_checks`（`evaluation.py:117-123`）は「複利リターンがプラス」かどうかしか見ていません。

- USD/JPY は 2023〜2026年に大きく円安が進んだ期間を含みます。この期間で**「ずっと買い持ち」と比べずに**SMA戦略がプラスでも、上昇トレンドの一部を取っただけかもしれません。
- さらに**スワップ（金利差）が未実装**です。USD/JPY の買い持ちは金利差を受け取る側です（仮に年4%なら、建玉20万円で年8,000円）。
  これは上の試算（期待利益 年約2万円）と同じ桁で、**スワップを入れた買い持ちがSMAに勝つ可能性が十分あります**。
- 必要なもの: `buy_and_hold`（スワップ込み）と `cash` をベースラインとして同じ区間で計算し、**超過リターンがプラスであることを `candidate` の条件にする**。

### 2.2 統計的な偶然を排除していない

- `MIN_CLOSED_TRADES = 30` は件数の下限だけで、「平均損益がゼロと区別できるか」は検定していません。
  必要なもの: トレード損益のブートストラップ信頼区間、またはシャープレシオの標準誤差。
- **試行回数が記録されない**: `evaluate` は同じデータに対して、パラメータを変えながら何度でも実行できます。20通り試せば、偶然1つは `candidate` になり得ます。
  必要なもの: 実験台帳（データハッシュ × 設定ハッシュ × 日時 × 結果）と、試行回数で補正した判定（Deflated Sharpe Ratio など）。`runs/` には出力が既に残るので、そこへの追記から始められます。
- **最終ホールドアウトがない**: 全区間が毎回評価に使われます。直近の一定期間を「最終確認まで一度も見ない」区間としてロックする仕組みが必要です。

### 2.3 指標が足りない

`performance_metrics`（`backtest.py:74`）には次がありません。

- 年率換算リターン、シャープ／ソルティノ、カルマー（年率リターン ÷ 最大DD）
- 回転率、総損益に占めるコストの比率
- 平均保有時間、スワップ損益

これがないと、目標（第1章）との照合や、ストレス条件で何%削られたかの判断ができません。

## 3. データ: 評価ゲートを通せるデータを作れない

| | 評価ゲートの要求 | 手元の実データ |
| --- | --- | --- |
| 本数 | 2,000本以上 | 239本 |
| 期間 | 180日以上 | 約12日（2026-09-06〜09-18） |

必要な作業に対して、現状のツールが次の点で詰まっています。

- `fetch-fx` は1回で最大367日（`gmo.py:77`）、しかも**出力ファイルを上書き**します（`data.py:write_bars`）。長期データを作るには、手作業で連結・重複排除する必要があります。
- 取得は1日ごとにBID/ASKの2リクエストを直列で送ります（3年分で約2,200回）。リトライも待機制御もないため、途中で1回失敗すると全体が失敗します。「失敗を空データで隠さない」方針は正しいですが、**途中から再開する仕組み**がありません。
- GMO の過去足は 2023-10-28 以降しか取れません（`gmo.py:72`）。3年弱・ほぼ円安局面だけの期間で、**相場環境の多様性が不足**します。
- 必要なもの:
  - `fetch-fx --append`（既存Parquetへの差分追記・重複検証・欠損区間レポート）
  - 取得失敗日からの再開
  - 長期の別データソース（2010年代を含む、BID/ASK付き）の取り込みアダプター。検証用に限り、GMOとの価格差も記録する
  - 欠損足・週末以外のギャップ検出（既存レビューの指摘と同じ）

## 4. 戦略: 試せる数が少なすぎる

- 戦略は `strategy.py` の `wants_long` 1関数に直書きされ、`Settings` は `extra="forbid"` で `fast` / `slow` 以外のパラメータを持てません。**新しいアイデアを試すたびに共通コアを書き換える構造**です。
  必要なもの: 戦略インターフェース（シグナル・建玉・パラメータ定義）と、戦略ごとの設定。バックテストと模擬売買で同じ実装を使う現方針はそのまま維持します。
- **買いのみ**: FXでは売りからも同様に利益機会があります。USD/JPY の買いのみは、実質的に「ドル高に賭け続ける」ことと同じです。売りを入れるとスワップの支払いが発生するため、スワップの実装とセットで必要です。
- **1銘柄のみ**（`config.py:39` で USD_JPY の1時間足に固定）: 個人の小さなエッジを積み上げるには、相関の低い複数の通貨ペアや時間軸に分散しないと、リスク当たりの収益が伸びません。
- **エグジット規則がない**: 利確・損切り・時間切れがなく、決済はシグナル反転のみです。

## 5. フォワード検証と運用: 動いていない

`runs/paper.sqlite` の実データ:

```text
events: 61（2026-09-22 08:11 〜 23:27 UTC）
内訳: same_signal 45 / hold 15 / buy 1
state: units 1,267 / equity 999,636 円 / halted false
```

- **定期実行がない**: README にある通り常駐も定期実行もないため、フォワード検証の記録が伸びません。バックテストの結論を信用できるかは、数か月分のフォワード記録で確かめるしかありません。
  必要なもの: Windows タスクスケジューラ（毎時、足の確定直後）への登録手順、失敗時の通知、停止を検知する死活監視。
- **バックテストと模擬売買の差を測っていない**: 模擬売買は実際の Bid/Ask で約定し、バックテストは固定コストの仮定で約定します。同じ期間で両者を並べて**想定コストと実測コストの差**を出すレポートがないため、第2章のコスト前提が正しいか確認できません。これが稼ぎの精度に最も直結する計測です。
- **既知の先読みバグが未修正**: `paper.py:48` は今も `quote.timestamp`（最大10秒未来を許容）で確定足を判定しています。既存レビューの指摘通り、`now` 基準にすべきです。
- 実弾に進む前に必要なもの（既存レビューの第6章に同意）: GMO Private API アダプター、注文IDと口座残高の照合、キルスイッチ、APIキーの保管方法、接続断からの復帰。

## 6. お金の出口: 税・記録

- 国内FXの利益は申告分離課税（20.315%）です。**年間損益・スワップ・手数料を確定申告用に出力する機能**が必要です。詳細は税理士か国税庁の資料で確認してください。
- 模擬口座・実口座ともに、**月次の損益報告**（実現損益、評価損益、スワップ、コスト、ベンチマーク比）がありません。「稼げているか」を定期的に判断する材料になります。

## 8. 次の一手（最小の具体案）

1. `fetch-fx --append` を作り、2023-10-28 以降の USD/JPY 1時間足を全部貯める（P0）。
2. `evaluate` に `buy_and_hold` ベースラインと、GMOの公開情報から設定したスワップ率を入れ、SMA 12/48 が**買い持ちに勝つか**を確認する（P0）。
   - 勝てなければ、それが現時点での重要な結論です。戦略の探索（P1の台帳と戦略インターフェース）へ進みます。
3. 並行して `paper-step` をタスクスケジューラで毎時実行し、フォワード記録を貯め始める（P1）。1か月後に、バックテストとのコスト差レポートで前提を検証する。
4. 第1章の試算を目標値に置き換え、**レバレッジなしで目標に届くか**を判断する。届かなければ、P3（証拠金モデル）の優先度を上げる。
