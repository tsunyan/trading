## 結論

停止を永続化し、OSロックで所有者の不在を確かめ、明示的な復旧でしか再開しない設計が、新しいモジュール全体で一貫しています。
結果不明を成功と見なさない方針も各所で守られており、テストも厚く揃っています。
区間切替で旧区間を同じDBに残し、ACK不明や未計上の約定がある区間を切り替えない設計も妥当です。
定期観測（`paper_runner`）と通知の部分には大きな問題はありませんでした。

一方で、このブランチの目的である長時間の口座同期を妨げる停止条件が4つありました。
どれも安全側に止まるもので、誤った計上や発注にはつながりません。ただし通常の運用で起こる出来事で止まり、そのたびに人が復旧する必要があります。

- 指摘1: POST制御を紐付けると、トークン操作が1回失敗しただけで、GET制御と同期環境ごと使えなくなります。復旧手段がありません。
- 指摘2: 口座の変化がRESTに先に反映され、通知がまだ届いていないと、継続同期が永続停止します。
- 指摘3: 正常終了でも、REST取得が2秒以内に終わらなければ永続停止になります。
- 指摘4: アーカイブの全件監査が履歴の量に比例し、監視タスクが毎分2回実行します。約10か月で監視タスクが実行上限を超える見込みです。

## 指摘

### 1. トークン操作の失敗1回で、POST制御が復旧できない停止になる（重要）

- 場所: `src/trading/post_control.py:395`（`operation()` の例外処理）、`:262`（`stop()`）、`src/trading/private_stream_token.py:280`・`:312`・`:337`（`acquire`・`maintain`・`close` の `limiter.stop()`）、`src/trading/private_sync.py:545`
- 内容:
  - `private_sync run` は、GET制御にPOST制御が紐付いていれば、トークンの取得（POST）・更新（PUT）・削除（DELETE）をすべて `PersistentPostLimiter.slot()` の中で行います。
  - 枠の中で例外が出ると、`operation()` は `operation_unknown` でSTOPPEDを保存します。トークンクライアントも失敗時に `limiter.stop()` を呼びます。
  - POST制御には復旧・解除の手段がありません（`docs/post-control.md` にも書かれています）。GET制御は別のPOST制御への付替えを拒否し、同期環境は1つのGET制御にしか紐付けられません。`run` はPOST制御が停止していると開始前に拒否します。
  - そのため、HTTP 5xx・タイムアウト・メンテナンス応答が1回あるだけで、GET制御・同期環境・POST制御をすべて作り直すことになります。
  - 継続同期では、トークン操作が1日に30〜40回あります。死活確認の記録で既定の1,024記録が約4時間で埋まり、そのたびに予定切替でPOSTとDELETEを行い、接続中も約50分ごとにPUTを行うためです。GMOの定期メンテナンスをまたいで動かせば、ほぼ確実にどこかで失敗します。
  - トークン操作の結果が不明でも、残るのは60分で失効するトークンだけで、注文は発生しません。注文と同じ「結果不明」として扱い、将来の発注まで止める必要はありません。
- 再現（一時テスト）:
  - トークン取得に503を返すと、POST制御は `STOPPED / operation_unknown` になりました。既存テスト `test_token_http_failure_leaves_durable_claim_and_sanitizes_remote_secrets` も同じ挙動を固定しています。
  - 同じGET制御に `PersistentPostLimiter.create` を再度呼ぶと、`post_control_already_bound` で拒否されました。
  - トークン更新の時刻に別のインスタンスがOSロックを保持していると、更新は `post_owner_busy` で失敗し、POST制御は `STOPPED / operator_stop` になりました。操作者は何もしていないのに、理由は `operator_stop` と記録されます。いまは注文送信の経路がないため起きませんが、注文クライアントを同じPOST制御につなぐと、更新と注文の競合で起きます。
- 提案（いずれか）:
  - 結果別の復旧を実装するまでは、トークン操作を永続POST制御に通さず、プロセス内の `PrivateStreamLimiter` で間隔を守る。
  - `private_stream` の結果不明を注文の結果不明と分け、トークン操作だけを再試行できる停止にする。
  - あわせて、トークンクライアントから呼ばれる `stop()` には `operator_stop` 以外の理由を記録する。

### 2. REST側の変化が通知より先に見えると、継続同期が永続停止する（重要）

- 場所: `src/trading/private_supervisor.py:248`、`:253`〜`261`、`src/trading/account_sync.py:399`
- 内容:
  - Supervisorは、取得結果に `balance_change_unverified` 以外の不一致があれば `sync_failed` で永続停止します。残高・建玉の照合（`compare_account_inventory`）が一致しない場合も同じです。
  - 取得中に通知が届けば、古い結果を捨てて再試行します（`RETRYABLE`）。しかし、口座の変化がRESTの応答に反映された時点で対応するWebSocket通知がまだ届いていないと、`order_change_without_event` などの不一致になり、その場で停止します。救われるのは、取得の受理から `_drain()` までの間（`run` の待機20msと1回の `step()`）に届いた通知だけです。
  - 逆向きも起こりえます。約定通知が先に届き、RESTの注文・約定一覧にまだその約定が見えないと、約定は計上されないまま残高照合だけが行われます。このときRESTの残高だけが先に決済損益を反映していれば、残高不一致で停止します。
  - 発注しない読取運用でも、手動の取消・決済、指値・逆指値の約定のたびにこの競合が起こりえます。通知の遅延を0.3秒と仮定すると、15秒周期の取得と重なる確率は1件の変化あたり数%です（遅延は仮定で、実APIでは確認していません）。
  - 停止のたびに `recover` が必要です。`main` にはSupervisorがなく、不一致はNEEDS_RESYNCとして次の取得で解消できました。このブランチで、不一致が致命的な扱いに変わりました。
- 再現（一時テスト）: 1回目の取得では有効注文があり、2回目の取得では通知が届かないままその注文がRESTから消えている状態にしました。2回目の照合で `SupervisorError("sync_failed")` になり、制御は `STOPPED / sync_failed` になりました。
- 提案: 構造の不一致と残高不一致は、受信を続けたまま上限付きで再取得する。同じ不一致が連続して残る場合（例えば `max_sync_retries` 回、または受信の期限まで）だけ停止する。通知が届けば、次の取得では保留中のイベントとして一致します。

### 3. 正常終了でも、REST取得が2秒以内に終わらなければ永続停止になる

- 場所: `src/trading/private_supervisor.py:45`（`join_timeout_seconds=2.0`）、`:412`〜`416`
- 内容:
  - `close()` は、動作中のRESTワーカーを `join_timeout_seconds`（既定2秒）だけ待ちます。終わらなければ `worker_not_joined` で `_abort()` し、STOPPEDを保存します。
  - `--duration-seconds` の満了とCtrl+Cは、どちらもこの経路を通ります。拘束照合を使う台帳では、1回の取得が「口座3回、有効注文ごとに4回、口座3回」のGETになり、250ms間隔の制限では有効注文が3件でも約4.5秒かかります。15秒周期のうち、取得中に止める確率は1割を超えます。
  - 期限を過ぎたワーカーを強制終了しない方針は妥当です。ただし取得は `collection_limit_seconds`（30秒）で必ず終わるので、終了時に2秒で諦める必要はありません。
- 再現（一時テスト）: 3秒かかる取得の最中に `close()` を呼ぶと、`worker_not_joined` で `STOPPED` になりました。取得自体は3秒で正常に終わっています。
- 提案: 終了処理では新しい取得を始めず、ワーカーを `sync_timeout_seconds` の残り時間まで待つ。

### 4. アーカイブの全件監査が履歴の量に比例し、監視タスクが毎分2回実行する

- 場所: `src/trading/segmented_journal.py:77`（開くたびに `audit_history()`）、`:301`・`:335`（切替のたびに2回）、`src/trading/stream_control.py:269`（`check_binding()` でも監査）、`src/trading/private_sync.py:228`・`:233`、`src/trading/private_operations.py:286`
- 内容:
  - `SegmentedEventJournal` は、開くたびに保存済みの全区間・全記録を検証します。`StreamControl.check_binding()` も `audit_history()` を呼びます。
  - Private監視タスク（60秒周期、実行上限90秒）は、`PrivateSyncWorkspace` を開くたびにこの全件監査を2回行います。継続同期の開始では、Workspaceを開く、Supervisorを作る、開始する、最初の区間切替をする、の各段階で合わせて6回行います。
  - このPCでは、3,624記録の監査に93ms（1記録あたり約26µs）かかりました。死活確認だけで1日あたり約5,800記録（30秒ごとに死活確認とACKの2件）増えます。1か月で監視1回あたり約9秒、約10か月で監視タスクが90秒の上限を超える見込みです。上限を超えると、障害を通知する仕組みそのものが止まります。
  - 切替時の監査は書込みトランザクションの中で行うため、その間はジャーナルの書込みロックが続き、監視側の読取がbusyで失敗しやすくなります。監視では `private_sync_unavailable` の発生と解消が繰り返し記録されます。
- 提案: 監視や通常の開き直しでは末尾のアンカー（`_anchor`）だけを検証し、全件監査は明示的な `audit_history()` と切替の前に限る。毎回全件を監査するなら、監査済みの `series.head` を保存しておき、差分だけを検証する。

### 5. 登録スクリプトのテストが、日本語版Windowsの既定のコンソールで失敗する

- 場所: `tests/test_private_tasks.py:92`、`scripts/install-private-watchdog.ps1:23`
- 内容:
  - テストはPowerShellの出力をUTF-8として読みます。Windows PowerShell 5.1の `ConvertTo-Json` の結果はコンソールのコードページで出力され、テスト用ディレクトリ名には日本語が含まれます。
  - コードページ932（日本語版の既定）のコンソールでは、デコードに失敗して `json.loads(None)` になり、テストが失敗します。UTF-8のコンソールでは合格するので、文書の「1661テストが合格」は実行環境に依存します。
  - タスク登録そのものには影響しません。Pythonが出すJSONはASCIIのみで、PowerShellの中で正しく復元されます。
- 提案: `-PlanOnly` ではPythonが返したJSON（`$planText`）をそのまま出力する。またはスクリプトの冒頭で `[Console]::OutputEncoding` をUTF-8にする。`install-paper-tasks.ps1` も同じ書き方です。

### 6. 軽微な点

- `private_sync` の `main()`（`src/trading/private_sync.py:723`）は、どの例外でも「Private sync failed; inspect local control state.」だけを出します。`private_operations` も `private_operations_failed` だけです。`PrivateSyncError`・`StreamControlError`・`SupervisorError` は秘密情報を含まない固定コードとして作られているので、これらに限って理由を表示すれば、`sync_dependencies_blocked` と `sync_checkpoint_changed` などを区別できます。
- `stream_binding`（`src/trading/read_control.py:292`）には、`post_binding` にある履歴側の記録（`POST_BOUND` イベント）がありません。表が欠落すると、別のSupervisorを紐付けられます。POST側と同じ検査に揃えるとよいです。
- `PrivateOperations` の通知は10,000件が上限で、超えると `check()` が毎回 `operations_alert_capacity` で失敗します（`src/trading/private_operations.py:271`）。状態が変わるたびに発生と解消の2件が増え、整理する手段がありません。上限に達すると監視は失敗し続け、そのことも通知されません。
- 監視は所有者の有無を確かめるため、60秒ごとに `StreamControl` のOSロックを短時間取ります（`src/trading/private_operations.py:288`）。その瞬間に `run`・`recover`・`reconcile-stopped` を始めると、`stream_owner_busy` で拒否されます。停止状態は保存されないので再実行すれば済みますが、文書に書いておくとよいです。
- `install-paper-tasks.ps1` は既存タスクの説明だけを確かめ、`install-private-watchdog.ps1` にある所有者SIDの確認をしていません。

## 確認したが問題としなかった点

- `paper_runner` は、時間切れのワーカーを結果不明として記録し、次の再試行に任せます。約定のcommit後に再試行しても二重約定しないことは、テストと `docs/paper-operations.md` の実機確認にあります。仮想環境のリダイレクタを避けて実体のPythonを起動するのも、時間切れでの終了を確実にするために妥当です。
- 監視の `check()` は、観測の実行中はロックを取れずに何もしません。ただし観測には時間上限があり、タスクにも実行上限があるので、止まったままにはなりません。
- `assert_rollover_ready()` と `end_for_rollover()` は、Captureのロックを保持したまま検査とEND記録を行い、`expected_head` で他の書込みを排除しています。途中で通知が割り込む余地はありません。
- 予定切替や復旧の途中（区間を回した後、制御DBを更新する前）でプロセスが止まっても、次の `recover` が空の新区間を受け入れ、制御DBを新しい区間に揃えます。
- `match_booked_events()` が再取得から外すのは、最後に保存したREST証拠が `EXECUTED` で、計上数量が注文数量と一致する注文だけです。完了済みの注文に新しい約定IDの通知が来れば、その注文ごと再取得します。
- `SubmissionReceipt` は、受付を約定や失効の確定に使わず、後のGET証拠とIDや状態が矛盾すれば停止します。注文POSTの実際の応答形式（MARKET注文で `price` が返るかなど）は、公式仕様と照合していません。

### 確認したこと

- 前回の一時テストを新しいコードで再実行しました。
  - 指摘1: 503の後は `STOPPED / operation_unknown`（claimは `token_acquire`）になり、3661秒後の `recover_token` でREADYに戻りました。更新時のロック競合では停止せず、ロックが空いた次の呼出しで更新されました。
  - 指摘2: 不一致は `pending_sync_reasons` に保留されて再取得され、通知が最後まで来ない場合は5回の再試行の後に `sync_failed` で停止しました。後から通知が届いて一致する場合は、Codexが追加した `tests/test_sync_notification_lag.py` で確かめられています。
  - 指摘3: 3秒かかる取得の最中に `close()` を呼ぶと、3.0秒待ってREADYで終わりました。
- トークン待機ループと時計の分解能: このPCのPython 3.12では `time.monotonic()` の分解能が15.625msで、短い待機の後に値が進まないことがあります。待機ループは、待機後に時計が進まなければ `clock_invalid`（`recover-token` の対象外）で停止するので、これが誤って起きるかを調べました。ループだけを写した模擬で72,000通り、実際のクラスで96通りの位相と処理時間を試し、一度も起きませんでした。問題ありません。
- `3eae332` で `uv run pytest -q` を実行し、1767件すべて合格しました（コードページ932のコンソール）。`uv run ruff check`、`uv run ruff format --check` も問題ありません。
